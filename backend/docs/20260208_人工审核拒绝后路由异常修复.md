# 人工审核拒绝后路由异常修复

## 问题描述

用户在 human_review 阶段拒绝审核并提交反馈后，工作流未按预期进入编辑循环并返回人工审核，而是在 structure_validation 节点结束。同时任务状态显示为 `processing` 而非 `human_review_pending`。

## 根因分析

### 原子事实

1. **工作流执行序列**（实际）：
   ```
   human_review (rejected) → edit_plan_analysis → roadmap_edit → structure_validation → END
   ```

2. **预期序列**：
   ```
   human_review (rejected) → edit_plan_analysis → roadmap_edit → human_review
   ```

3. **关键日志证据**：
   ```log
   [22:00:25] edit_plan_analysis_node_start  edit_source=validation_failed
   [22:06:29] route_after_edit_to_validation  edit_source=validation_failed
   [22:06:54] task_status_updated  current_step=human_review status=processing
   ```

### 逻辑公理

**LangGraph 状态合并规则**：
- 节点返回的字典会**合并**到 state 中
- 如果节点**不返回**某个字段，该字段保持原值（不会被删除）
- 路由函数读取的是**更新后的 state**（包含节点返回值）

### 因果推导

**问题1：edit_source 被错误继承**

1. 第一轮验证失败时，`structure_validation_node` 设置：
   ```python
   "edit_source": "validation_failed"  # structure_validation_node.py:100
   ```

2. 状态持久化到 LangGraph checkpoint

3. 用户拒绝审核，`human_review_node` **未返回** `edit_source` 字段

4. 恢复工作流时，`edit_plan_analysis_node` 从 state 读取：
   ```python
   edit_source = state.get("edit_source", "human_review")  # 已存在旧值
   ```
   由于 state 中**已存在** `"validation_failed"`，不使用默认值

5. `route_after_edit` 检查到 `edit_source="validation_failed"`，返回 `"structure_validation"` 而非 `"human_review"`

**问题2：任务状态未正确更新**

1. 工作流恢复时，`coordinator.on_node_start()` 将状态设置为 `"processing"`

2. `ReviewHandler.on_start()` 仅在**第一次进入**时调用，恢复时不会执行

3. `ReviewHandler._handle_output()` 在用户拒绝时**未更新状态**

4. 最终状态保持为 `"processing"` 而非 `"human_review_pending"`

## 修复方案

### 修复1：显式设置 edit_source

**文件**：`backend/app/core/orchestrator/nodes/human_review.py`

**修改**：在用户拒绝审核时，显式返回 `edit_source="human_review"`，覆盖 state 中可能存在的旧值

```python
return {
    "human_approved": approved,
    "user_feedback": feedback if not approved else None,
    "roadmap_id": roadmap_id,
    "current_step": (
        WorkflowStep.CONTENT_GENERATION_QUEUED.value 
        if approved 
        else WorkflowStep.HUMAN_REVIEW.value
    ),
    # ✅ 修复：拒绝时显式设置 edit_source 为 "human_review"
    "edit_source": "human_review" if not approved else state.get("edit_source"),
    "execution_history": [
        f"人工审核完成: {'批准' if approved else '拒绝'}"
    ],
}
```

### 修复2：每次进入 human_review 时更新状态

**文件**：`backend/app/core/orchestrator/nodes/human_review.py`

**修改**：在 `human_review_node` 函数开始时，显式将任务状态更新为 `"human_review_pending"`

**原因**：
- 用户拒绝后状态应为 `"processing"`（正确，因为会进入编辑流程）
- **再次进入 human_review 时**，状态才应更新为 `"human_review_pending"`
- `ReviewHandler.on_start()` 在重构后未被自动调用，需要在节点内部处理

```python
# ✅ 每次进入 human_review 节点时，更新任务状态为 human_review_pending
async with get_celery_session() as session:
    task_crud = get_task_crud()
    await task_crud.update_task_status(
        session=session,
        task_id=task_id,
        status="human_review_pending",
        current_step="human_review",
        roadmap_id=roadmap_id,
    )
```

## 验证方式

1. 生成一个路线图，等待进入 human_review
2. 拒绝审核并提交反馈
3. 检查日志：
   - `edit_plan_analysis_node_start` 应显示 `edit_source=human_review`
   - `route_after_edit_to_human_review` 应出现
4. 检查数据库：
   - `tasks.status` 应为 `human_review_pending`
   - `tasks.current_step` 应为 `human_review`

## 影响范围

- **影响模块**：LangGraph 工作流路由、人工审核流程
- **影响用户**：所有在 human_review 阶段拒绝审核的用户
- **数据迁移**：无需数据迁移
- **向后兼容**：完全兼容，修复为预期行为

## 技术要点

1. **状态合并语义**：LangGraph 不会自动清除未返回的字段，需要显式覆盖
2. **Handler 职责边界**：状态更新应由 Handler 完成，而非依赖 Coordinator
3. **路由函数纯度**：路由函数只读取 state，不修改状态
