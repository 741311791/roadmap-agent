# AI 伴学助手 — 后端生产级实施计划

## 一、文档目标

本文档用于重新定义 AI 伴学助手的后端实施方案。目标不是只完成一个“能聊天”的接口，而是建设一套可支撑真实生产流量、具备长期记忆能力、支持异步削峰、具备可观测性与容错能力的后端系统。

本次方案采用以下核心技术组合：

- `FastAPI`：负责高并发接入、鉴权、限流、流式输出
- `Redis`：负责短期记忆、Broker、分布式锁、幂等标记、限流
- `Celery`：负责异步持久化、记忆提炼、补偿任务、定时任务
- `PostgreSQL + PgVector`：负责消息归档、业务元数据、长期记忆向量存储
- `Mem0`：负责长期记忆提取、检索、合并、覆盖与演化

---

## 二、架构设计原则

### 2.1 核心原则

1. **请求快路径与记忆慢路径彻底解耦**
   - 用户对话主链路只做轻量操作，避免把“记忆提炼”和“持久化”塞进同步接口。
2. **短期记忆与长期记忆分层**
   - Redis 保存短期窗口上下文。
   - PgVector 保存长期稳定事实。
3. **写入最终一致，读取优先可用**
   - 消息归档和记忆沉淀允许异步完成，但对用户回复链路必须实时可用。
4. **按用户维度串行化长期记忆写入**
   - 同一用户的记忆提炼必须通过 Redis 分布式锁串行执行。
5. **所有关键任务必须支持重试、幂等、回补**
   - 不允许因为单次 LLM 或网络故障造成消息丢失或重复提炼。
6. **系统先支持单租户产品形态，但设计上保留多租隔离能力**
   - 所有核心表和缓存 Key 从一开始就按 `user_id` 隔离。

### 2.2 非功能性目标

- 对话接口 P95 延迟目标：`<= 2.5s + 上游模型首 Token 时间`
- Redis 读短期记忆耗时目标：`< 5ms`
- 长期记忆检索耗时目标：`< 80ms`
- 异步消息归档成功率目标：`>= 99.9%`
- 记忆提炼任务最终成功率目标：`>= 99.5%`
- 系统支持 Web 节点与 Worker 节点独立水平扩容

## 三、系统物理分层

### 3.1 接入与路由层：FastAPI Web Nodes

职责：

- 提供 `SSE` 或 `WebSocket` 流式对话接口
- 执行用户鉴权、权限校验、限流
- 读取 Redis 中的短期记忆
- 读取 Mem0 检索到的长期记忆
- 组装 Prompt 并实时调用 LLM
- 在响应结束后投递异步任务到 Celery

设计要求：

- 无状态部署，支持多实例横向扩容
- 不在 Web 节点中执行耗时记忆提炼
- 不在请求线程中写大量数据库事务
- 使用 Redis 进行轻量级会话状态协同

### 3.2 高速缓存与消息总线层：Redis

职责：

- 保存短期记忆窗口
- 作为 Celery Broker
- 保存分布式锁
- 保存限流计数器
- 保存幂等去重标记
- 保存会话级临时元数据

设计要求：

- 生产环境优先使用 Redis Cluster 或托管 Redis
- Key 必须统一命名、带 TTL、可观测
- 分布式锁必须设置超时和续约策略

### 3.3 异步计算层：Celery Worker Nodes

职责：

- 异步写入消息归档表
- 异步更新 Redis 短期记忆窗口
- 调用 Mem0 执行长期记忆提炼
- 执行失败重试、补偿和定时总结任务

设计要求：

- 按队列类型拆分 Worker 池
- 重任务与轻任务分开，避免互相阻塞
- 对调用外部 LLM 的任务启用指数退避重试

### 3.4 记忆与持久化层：PostgreSQL + PgVector + Mem0

职责：

- PostgreSQL 存储会话元数据、消息流水、任务审计日志
- PgVector 存储长期记忆向量
- Mem0 负责长期记忆提取、语义检索和记忆合并

设计要求：

- 消息归档表与向量记忆表分开
- 长期记忆必须支持 `user_id` 级别隔离
- 为高频查询字段建立 B-Tree 索引
- 为向量字段建立 `HNSW` 索引

## 四、核心数据流设计

### 4.1 流程 A：用户对话主链路

目标：保证接口响应时间主要受网络与 LLM 推理影响，而不是被记忆落盘与提炼拖慢。

#### 第一步：请求接入

FastAPI 接收：

- `user_id`
- `session_id`
- `message`
- `agent_type`
- `roadmap_id`
- `concept_id`
- `thread_id`

同时执行：

- JWT 鉴权
- 用户权限校验
- Redis 限流检查
- 请求体基础校验

#### 第二步：并发上下文组装

使用并发方式同时读取两类记忆：

- **短期记忆 STM**
  - 从 Redis 读取 `mentor:stm:{session_id}`
  - 只保留最近 `20` 条消息
- **长期记忆 LTM**
  - 调用 Mem0 `search()`，按 `user_id` 过滤
  - 查询与当前问题最相关的 Top-K 长期记忆

#### 第三步：Prompt 组装与模型生成

Prompt 由以下部分构成：

- System Prompt
- 当前章节上下文
- 召回的长期记忆摘要
- 短期对话窗口
- 本轮用户问题

然后通过流式方式调用 LLM，将结果持续返回前端。

#### 第四步：异步派发后处理任务

在流式输出完成后，FastAPI 不做重处理，只投递 Celery 任务：

- 任务类型：`persist_and_extract_memory`
- 载荷内容：
  - `message_id`
  - `user_id`
  - `session_id`
  - `thread_id`
  - `user_message`
  - `assistant_message`
  - `roadmap_id`
  - `concept_id`
  - `agent_type`
  - `model_id`
  - `trace_id`

### 4.2 流程 B：异步记忆沉淀链路

目标：保证对话数据最终不丢失，并在高并发下安全演化长期记忆。

#### 第一步：幂等检查

Worker 消费任务后，先检查：

- `mentor:task_done:{message_id}`

如果已存在，则直接跳过，避免重复落盘和重复提炼。

#### 第二步：短期记忆更新

Worker 将本轮 `user_message` 与 `assistant_message` 追加到 Redis：

- Key：`mentor:stm:{session_id}`
- 操作：`LPUSH` + `LTRIM 0 19`
- TTL：`24h`

#### 第三步：消息归档

将两条消息写入 PostgreSQL 消息流水表，作为审计、回放、回补和训练数据来源。

#### 第四步：长期记忆提炼

Worker 申请 Redis 分布式锁：

- `mentor:lock:memory:{user_id}`

拿到锁后调用：

- `mem0.add(messages=..., user_id=user_id, metadata=...)`

Mem0 内部完成：

- 新事实提取
- 与历史记忆比对
- 新增、合并或覆盖
- 写入 PgVector

#### 第五步：完成标记

处理成功后写入：

- `mentor:task_done:{message_id}`，TTL 建议 `7d`

## 五、短期记忆与长期记忆设计

### 5.1 短期记忆 STM

主存储：Redis  
备份来源：PostgreSQL 消息流水表

#### Redis Key 设计

```text
mentor:stm:{session_id}
```

#### 数据结构

- 使用 `List`
- 每个元素为一条序列化消息
- 消息结构建议包含：
  - `message_id`
  - `role`
  - `content`
  - `created_at`

#### 管理策略

- 滑动窗口保留最近 `20` 条
- TTL 设为 `24h`
- 每次新消息到达时续期

#### Cache Miss 回补策略

Redis 丢失会话时，Web 层执行以下回补：

1. 查询 PostgreSQL 中该 `session_id` 最近 `20` 条消息
2. 回写 Redis 列表
3. 重新设置 TTL

### 5.2 长期记忆 LTM

主存储：PostgreSQL + PgVector  
编排方式：Mem0 SDK

#### 存储原则

- 只沉淀“稳定、可复用、与用户长期相关”的事实
- 不把所有原始消息都塞进向量库
- 每条长期记忆都必须与 `user_id` 绑定

#### 典型记忆内容

- 用户掌握程度
- 常见误区
- 偏好的解释方式
- 学习节奏
- 当前学习目标与阶段

#### 检索策略

- `user_id` 过滤 + 语义向量召回
- Top-K 默认建议 `3~5`
- 检索结果在进入 Prompt 前做简短归纳，防止上下文膨胀

## 七、Redis Key 设计规范

### 7.1 Key 命名

```text
mentor:stm:{session_id}
mentor:lock:memory:{user_id}
mentor:ratelimit:user:{user_id}
mentor:ratelimit:ip:{ip}
mentor:task_done:{message_id}
mentor:session:meta:{session_id}
mentor:ws:connection:{session_id}
```

### 7.2 TTL 建议

| Key 类型 | TTL |
|---|---|
| `mentor:stm:*` | 24 小时 |
| `mentor:lock:memory:*` | 30 秒，需支持续约 |
| `mentor:ratelimit:*` | 按限流窗口配置 |
| `mentor:task_done:*` | 7 天 |
| `mentor:session:meta:*` | 24 小时 |

### 7.3 分布式锁要求

- 使用唯一随机值作为锁值
- 释放锁时校验锁值归属
- 防止误删其他 Worker 持有的锁
- 任务执行较长时必须支持锁续约

## 十、Agent 与 Prompt 设计

仍然保留双模式，但不再把它视为单纯 Prompt 切换，而是明确的产品角色：

- `tutoring`
  - 偏启发式、苏格拉底式引导
- `company`
  - 偏陪伴式解释、情绪支持与鼓励反馈

### 10.2 Prompt 组装层次

最终 Prompt 建议由以下部分组成：

1. 固定系统角色 Prompt
2. 章节上下文
3. 用户长期记忆摘要
4. 最近短期对话窗口
5. 当前问题
6. 回复约束

### 10.3 Prompt 模板要求

`tutorin_agent.j2` 与 `company_agent.j2` 必须支持：

- `concept_title`
- `tutorial_excerpt`
- `roadmap_context`
- `ltm_facts`
- `learning_profile`

要求：

- 导学模式强调提问式引导
- 伴学模式强调解释清晰与正向反馈

## 十一、Celery 队列规划

建议拆分三个队列：

### 11.1 `mentor_persist`

职责：

- 写消息流水
- 更新 Redis STM
- 更新会话元数据

特点：

- 轻任务
- 低延迟
- 可高并发消费

### 11.2 `mentor_memory`

职责：

- 调用 Mem0 提炼长期记忆
- 执行用户级串行写入

特点：

- 重任务
- 受外部 LLM 延迟影响大
- 需要强重试策略

### 11.3 `mentor_reflection`

职责：

- 每日对长对话做阶段性总结
- 生成更高阶的用户画像或学习偏好记忆

特点：

- 定时任务
- 非实时
- 可在低峰期集中执行

## 十二、可靠性设计

### 12.1 重试机制

对以下异常启用自动重试：

- LLM API `429`
- LLM API `502/503/504`
- Mem0 网络超时
- PostgreSQL 短暂连接失败

Celery 策略建议：

- `autoretry_for`
- `retry_backoff=True`
- `retry_jitter=True`
- 最大重试次数建议 `5`

### 12.2 幂等机制

每轮对话生成唯一 `message_id`，并在异步任务开始前检查：

- Redis 去重 Key
- PostgreSQL `message_id unique`

双保险保证：

- Redis 用于快速拦截重复任务
- PostgreSQL 用于最终约束

### 12.3 死信与补偿

连续重试失败后：

- 将任务状态更新为 `dead_letter`
- 写入 `mentor_memory_jobs`
- 允许后台手动重放

### 12.4 Redis 故障降级

若 Redis STM 读取失败：

- 降级为直接读取 PostgreSQL 最近消息
- 本轮请求仍可继续

若 Redis Broker 故障：

- 对话接口仍可继续返回
- 但需要把异步投递失败记录到数据库补偿表，等待后台扫描重投

## 十四、安全与风控设计

### 14.1 鉴权

- 所有用户接口必须基于 JWT
- 所有查询都必须按 `user_id` 过滤

### 14.2 限流

建议至少两层限流：

- `user_id` 维度
- `IP` 维度

建议指标：

- 每分钟请求次数
- 每日总对话次数
- 单会话并发发送限制

### 14.3 输入治理

- 限制单条用户消息长度
- 限制历史窗口长度
- 对 `tutorial_excerpt` 截断
- 过滤极端超长上下文

### 14.4 数据隔离

- Redis Key 按 `session_id` 与 `user_id` 组织
- PostgreSQL 查询必须带用户过滤
- 向量检索必须带 `user_id` filter

## 十五、部署与伸缩建议

### 15.1 部署单元

建议拆分为四类运行单元：

1. FastAPI Web
2. Celery Persist Worker
3. Celery Memory Worker
4. Celery Beat

## 十八、落地时的关键决策

1. **消息归档必须上服务端**
   - 不能只依赖前端 localStorage，否则无法做跨端同步、审计、回补与记忆训练。
2. **长期记忆提炼必须异步**
   - 不能放在主请求链路。
3. **同一用户的长期记忆写入必须串行**
   - 否则高并发下会出现重复提炼和脏覆盖。
4. **Redis 必须同时承担 STM、Broker、锁与幂等标记**
   - 这是该架构的关键润滑层。
5. **消息流水表与向量记忆表必须分离**
   - 原始数据归档与语义记忆是两种不同职责。

## 十九、结论

当前 AI 伴学助手后端不应该只实现一个简单的 SSE 聊天接口，而应该建设为一套“快路径同步响应 + 慢路径异步沉淀 + Redis 润滑 + PgVector 深记忆”的生产级系统。

最终推荐架构是：

- `FastAPI` 承担高并发接入与流式响应
- `Redis` 承担 STM、Broker、锁、限流、幂等
- `Celery` 承担异步持久化与记忆提炼
- `Mem0 + PgVector` 承担长期记忆检索与演化
- `PostgreSQL` 承担全量消息归档与审计

这套方案能够同时满足实时性、稳定性、可扩展性与长期认知能力，适合作为生产级 AI 陪伴助手的后端基线架构。
