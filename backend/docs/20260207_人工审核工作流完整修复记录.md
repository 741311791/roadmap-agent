# 人工审核工作流完整修复记录

## 问题背景

用户在测试人工审核功能时遇到一系列问题，从 Celery Worker 启动失败到工作流循环再到内容生成数据缺失。

## 修复问题汇总

### 问题 1: Celery Worker 启动失败（macOS SIGKILL）

**现象**：
```
[ERROR] Process 'ForkPoolWorker-3' pid:25259 exited with 'signal 9 (SIGKILL)'
[CRITICAL] Unrecoverable error: WorkerLostError('Could not start worker processes')
```

**根本原因**：
- macOS 的 fork 机制对复杂异步操作支持不佳
- 使用 prefork pool 时，部分 worker 进程被系统 SIGKILL 杀死

**解决方案**：
修改 `Makefile`，macOS 开发环境使用 solo pool：

```makefile
# 检测操作系统
UNAME_S := $(shell uname -s)
ifeq ($(UNAME_S),Darwin)
    CELERY_POOL := solo
    CELERY_CONCURRENCY_WORKFLOW := 1
    CELERY_CONCURRENCY_CONTENT := 1
else
    CELERY_POOL := prefork
    CELERY_CONCURRENCY_WORKFLOW := 8
    CELERY_CONCURRENCY_CONTENT := 20
endif
```

**修改文件**：
- `Makefile` (line 189-211)

### 问题 2: 测试脚本 API 端点错误

**现象**：
```
RuntimeError: 登录失败: {"error":{"code":"NOT_FOUND"...}}
```

**根本原因**：
- FastAPI Users 的登录端点路径不正确
- 响应格式与项目自定义 API 不同

**解决方案**：
修正 API 端点和响应格式处理：

| 功能 | 错误 | 正确 |
|-----|------|------|
| 登录端点 | `/api/v1/auth/login` | `/api/v1/auth/jwt/login` |
| 登录方式 | JSON `{email, password}` | Form data `{username, password}` |
| 登录响应 | `data["data"]["access_token"]` | `data["access_token"]` |
| 用户信息响应 | `data["data"]` | `data`（直接返回用户对象） |
| 任务列表端点 | `/api/v1/tasks/users/{user_id}` | `/api/v1/tasks/my`（JWT 自动提取） |

**修改文件**：
- `backend/scripts/test_human_review.py` (line 66-90, 349-374, 420-421)

### 问题 4: 审批后工作流陷入循环（核心问题）

**现象**：
```
workflow_resumed_successfully → final_step=human_review
workflow_paused_for_review_again → 又回到 human_review 状态
```

**根本原因**：
`human_review_node` 无论批准还是拒绝都返回 `current_step="human_review"`，导致 Service 层误判工作流又暂停了。

**代码分析**：

```python
# ❌ 错误代码（human_review.py line 231）
return {
    "human_approved": approved,
    "current_step": "human_review",  # 问题：批准时也返回 human_review
}

# Service 层判断（workflow_execution_service.py line 368）
if current_step == "human_review":  # ❌ 即使批准也会进入此分支
    status = TaskStatus.HUMAN_REVIEW
    logger.info("workflow_paused_for_review_again")
```

**解决方案**：

1. **修改 human_review_node 返回值**：

```python
# ✅ 正确代码（human_review.py line 231）
return {
    "human_approved": approved,
    "current_step": "completed" if approved else "human_review",
    # 批准 → completed（工作流结束）
    # 拒绝 → human_review（等待下次审核）
}
```

2. **改进 Service 层判断逻辑**：

```python
# ✅ 正确代码（workflow_execution_service.py line 364-385）
human_approved = final_state.get("human_approved", False)

if current_step == "human_review" and not human_approved:
    # 用户拒绝，暂停
    status = TaskStatus.HUMAN_REVIEW
elif current_step == "completed" or human_approved:
    # 批准或已完成
    status = TaskStatus.COMPLETED
```

**修改文件**：
- `backend/app/core/orchestrator/nodes/human_review.py` (line 231)
- `backend/app/services/workflows/execution/workflow_execution_service.py` (line 363-395)

**验证日志**：
```
✅ current_step: 'completed' - 节点返回正确状态
✅ workflow_resumed_successfully final_step=completed
✅ workflow_completed_after_review approved=True
✅ content_generation_task_triggered
```

### 问题 5: 内容生成缺少用户偏好数据

**现象**：
```
ValidationError: 5 validation errors for LearningPreferences
learning_goal: Field required
available_hours_per_week: Field required
...
```

**根本原因**：
缓存数据中没有保存 `user_request` 对象，只保存了 `user_constraints`。

**代码分析**：

```python
# human_review.py - 缓存写入
cache_data = {
    "user_constraints": user_constraints,  # ✅ 有
    # ❌ 缺少 user_request
}

# content_generation_tasks.py - 缓存读取
user_request = cache_data.get("user_request", {})  # 返回空字典
preferences_data = user_request.get("preferences", {})  # 再次返回空字典
user_preferences = LearningPreferences(**preferences_data)  # ❌ 验证失败
```

**解决方案**：
在缓存数据中添加 `user_request` 字段：

```python
# ✅ 正确代码（human_review.py line 93）
cache_data = {
    "roadmap_id": roadmap_id,
    "framework": framework.model_dump(),
    "concepts": [c.model_dump() for c in concepts],
    "user_constraints": user_constraints,
    "user_request": user_request.model_dump() if user_request else {},  # ✅ 新增
    "cached_at": datetime.utcnow().isoformat(),
    "version": "v1",
}
```

**修改文件**：
- `backend/app/core/orchestrator/nodes/human_review.py` (line 93)

### 问题 7: 测试脚本硬编码 user_id

**现象**：
- `test_roadmap_generation.py` 中 `user_id` 被硬编码为 `"e2e-test-permanent-user-id-00000001"`
- 与实际登录用户 ID 不匹配，导致数据关联错误

**根本原因**：
脚本未从登录响应中获取实际的 user_id

**解决方案**：
修改登录函数返回用户 ID，并在请求中使用：

```python
# ✅ 修改 1: 登录函数返回 (token, user_id)
async def login_and_get_token(client: httpx.AsyncClient) -> tuple[str, str]:
    token = response.json()["access_token"]
    
    # 获取用户信息
    user_response = await client.get("/api/v1/users/me", ...)
    user_id = user_response.json()["id"]
    
    return token, user_id

# ✅ 修改 2: 提交请求时使用实际 user_id
async def submit_roadmap_generation(client, token, user_id):
    request_data = {
        "user_id": user_id,  # 使用实际 ID
        ...
    }

# ✅ 修改 3: main 函数中解包
token, user_id = await login_and_get_token(client)
task_id = await submit_roadmap_generation(client, token, user_id)
```

## 技术要点总结

### 1. macOS Celery Worker 最佳实践

- ✅ 使用 `--pool=solo` 避免 fork 问题
- ✅ 设置 `--concurrency=1` 单进程模式
- ❌ 避免使用 `prefork` pool（Linux 生产环境才用）

### 2. FastAPI Users vs 自定义 API

| 特性 | FastAPI Users | 项目自定义 API |
|-----|--------------|--------------|
| 响应格式 | 直接返回数据 | `{data: {...}}` 包装 |
| 登录端点 | `/auth/jwt/login` | `/auth/login` |
| 登录方式 | Form data | JSON |
| 用户端点 | `/users/me` | `/users/profile` |

### 3. LangGraph Interrupt 工作流

```python
# 节点中暂停
resume_value = interrupt({...})  # 暂停，等待外部输入

# 恢复时传递数据
Command(resume={"approved": True, ...})  # 恢复并传递决策

# 路由根据状态字段决定分支
if state.get("human_approved"):
    return "approved"  # 进入批准分支
```

### 4. 缓存数据完整性

内容生成需要的数据：
- ✅ `framework`: 路线图结构
- ✅ `concepts`: Concept 列表
- ✅ `user_constraints`: 来自 IntentAnalysis
- ✅ `user_request`: **关键**，包含 `preferences`（用户偏好）
