# 数据库超时与连接稳定性修复（架构优化版）

**日期**: 2026-01-26  
**问题来源**: 生产环境日志分析（err.log 第 182-240 行）  
**影响范围**: 数据库连接、WebSocket 推送、Redis 连接  
**最终方案**: 架构重构 - 独立内容生成 Worker

---

## 一、问题分析

### 1.1 核心问题：PostgreSQL 连接超时

**错误信息**:
```
psycopg.OperationalError: consuming input failed: could not receive data from server: Operation timed out
```

**发生位置**: LangGraph checkpoint 保存时  
**根本原因**: 
- LangGraph 保存 checkpoint 时执行的操作可能较为耗时
- 当前数据库超时配置不足以应对高负载或网络延迟场景
- 原配置: `command_timeout=180s`, `timeout=60s`

**影响**:
- 导致工作流执行失败
- 触发一系列后续错误（WebSocket 推送失败、Redis 连接异常等）

---

### 1.2 次要问题：WebSocket 竞态条件

**错误信息**:
```
RuntimeError: 'Cannot call "send" once a close message has been sent.'
```

**发生位置**: `_send_current_status` 和 `_forward_redis_events` 函数  
**根本原因**:
- 虽然检查了 `websocket.client_state == WebSocketState.CONNECTED`
- 但在检查和发送之间，连接状态可能已经改变
- 存在典型的 **检查-使用时间差 (TOCTOU)** 竞态条件

**原代码逻辑**:
```python
# ❌ 存在竞态条件
if websocket.client_state == WebSocketState.CONNECTED:
    await websocket.send_json(...)  # 这里连接可能已经关闭
```

---

### 1.3 其他问题

#### 1.3.1 Redis 连接关闭错误
**错误**: `Event loop is closed`  
**原因**: 在 event loop 关闭后尝试关闭 Redis 连接  
**影响**: 日志中出现 WARNING，但不影响功能

#### 1.3.2 404 错误
**请求路径**: `/api/v1/tasks/{task_id}/edit/history-full`  
**实际路由**: `/api/v1/roadmaps/{roadmap_id}/edit/history-full`  
**原因**: 前端使用了错误的 API 路径  
**影响**: 前端无法获取编辑历史，需要前端修复

## 二、修复方案

### 2.1 增加数据库超时配置

**文件**: `backend/app/db/session.py`

**修改前**:
```python
connect_args={
    "command_timeout": 180,  # 3分钟
    "timeout": 60,           # 1分钟
}
```

**修改后**:
```python
connect_args={
    "command_timeout": 300,  # ✅ 5分钟 - 用于长时间运行的查询
    "timeout": 120,          # ✅ 2分钟 - 用于建立连接
}
```

**理由**:
1. **LangGraph checkpoint 保存操作可能耗时较长**
   - 需要序列化大量状态数据
   - 涉及多个数据库写操作
   - 在高并发场景下可能排队等待

2. **网络延迟和数据库负载**
   - 云数据库可能存在网络抖动
   - 高并发时数据库响应变慢
   - 需要更宽松的超时配置

3. **权衡考虑**
   - 5分钟的 command_timeout 不会导致资源长期占用
   - 仍然能够检测到真正的死锁或挂起
   - 符合 LangGraph 长时间操作的特点

---

### 2.2 修复 WebSocket 竞态条件

**文件**: `backend/app/api/v1/websocket.py`

**修改策略**: 移除错误情况下的消息发送，避免竞态条件

**修改前**:
```python
except Exception as e:
    logger.error("websocket_get_status_error", task_id=task_id, error=str(e))
    try:
        if websocket.client_state == WebSocketState.CONNECTED:
            await websocket.send_json({"type": "error", ...})  # ❌ 竞态条件
    except Exception as send_error:
        logger.debug("websocket_already_closed", ...)
```

**修改后**:
```python
except Exception as e:
    logger.error("websocket_get_status_error", task_id=task_id, error=str(e))
    # ✅ 不尝试发送错误消息，避免竞态条件
    # WebSocket 连接状态在检查和发送之间可能改变
```

**理由**:
1. **异常处理中发送消息风险高**
   - 异常往往意味着连接已经不稳定
   - 检查和发送之间存在时间差
   - 可能触发二次异常，污染日志

2. **客户端可以从日志和其他渠道感知错误**
   - WebSocket 断开本身就是一个信号
   - 客户端可以通过超时检测异常
   - 不需要在异常路径中强行推送

3. **简化错误处理逻辑**
   - 记录日志即可，无需额外操作
   - 避免嵌套的 try-except
   - 减少潜在的 bug

---

### 2.3 修复 Redis 连接关闭逻辑

**文件**: `backend/app/db/redis_client.py`

**修改点 1**: `connect()` 方法中的连接切换处理

**修改前**:
```python
if self._client is not None and self._loop_id != current_loop_id:
    try:
        await self._client.close()  # ❌ 可能在已关闭的 loop 上执行
    except Exception as e:
        logger.warning("redis_close_old_connection_failed", error=str(e))
```

**修改后**:
```python
if self._client is not None and self._loop_id != current_loop_id:
    try:
        # ✅ 检查事件循环是否还在运行
        try:
            asyncio.get_running_loop()
            await self._client.close()
        except RuntimeError:
            # Event loop 已关闭，直接清理引用
            logger.debug("redis_skip_close_event_loop_closed", ...)
    except Exception as e:
        logger.warning("redis_close_old_connection_failed", error=str(e))
```

**修改点 2**: `close()` 方法

**修改前**:
```python
async def close(self):
    if self._client:
        await self._client.close()  # ❌ 可能在已关闭的 loop 上执行
        self._client = None
        self._loop_id = None
```

**修改后**:
```python
async def close(self):
    if self._client:
        try:
            # ✅ 检查事件循环是否还在运行
            try:
                asyncio.get_running_loop()
                await self._client.close()
                logger.info("redis_client_closed")
            except RuntimeError:
                # Event loop 已关闭，直接清理引用
                logger.debug("redis_skip_close_event_loop_closed", ...)
        except Exception as e:
            logger.warning("redis_close_failed", error=str(e))
        finally:
            self._client = None
            self._loop_id = None
```

**理由**:
1. **Event Loop 生命周期管理**
   - asyncio 的资源（如连接）必须在对应的 loop 中关闭
   - 如果 loop 已关闭，尝试关闭连接会抛出 `RuntimeError`
   - 这种情况下直接清理引用即可

2. **优雅降级**
   - 无法关闭时记录日志，但不影响程序继续运行
   - 使用 `finally` 确保引用总是被清理
   - 避免内存泄漏

## 四、风险评估

### 4.1 数据库超时增加的风险

**潜在风险**:
- 真正的死锁或挂起需要更长时间才能被检测
- 数据库连接占用时间增加

**缓解措施**:
- 5分钟仍然是合理的超时时间
- 通过连接池配置 (`pool_timeout=60s`) 控制获取连接的等待时间
- 监控慢查询，优化性能瓶颈

**风险等级**: 🟢 低

---

### 4.2 WebSocket 错误消息移除的风险

**潜在风险**:
- 客户端在异常情况下无法收到明确的错误消息

**缓解措施**:
- 客户端可以通过连接断开感知异常
- 客户端可以实现超时和重试机制
- 服务端日志已记录详细错误信息

**风险等级**: 🟢 低

---

### 4.3 Redis 连接关闭逻辑修改的风险

**潜在风险**:
- 连接未正确关闭导致资源泄漏

**缓解措施**:
- Redis 连接池会自动管理连接生命周期
- 即使未显式关闭，连接也会在超时后被回收
- 使用 `finally` 确保引用总是被清理

**风险等级**: 🟢 低
