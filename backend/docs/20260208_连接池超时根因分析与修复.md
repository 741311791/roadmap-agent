# LangGraph Checkpoint 连接池超时根因分析与修复

## 问题症状

**错误信息**：
```
PoolTimeout: couldn't get a connection after 120.00 sec
```

**发生场景**：
- 在 `resume_after_human_review` 时，LangGraph 调用 `graph.aget_state(config)` 获取 checkpoint 状态
- 等待 120 秒后超时

**数据库连接状态**：
```sql
SELECT count(*), state FROM pg_stat_activity GROUP BY state;
-- 结果：
-- 6  (未知状态)
-- 1  active
-- 18 idle
-- 总计：25 个连接
```

**理论最大连接数**：
- SQLAlchemy 主池：`pool_size(8) + max_overflow(6) = 14`
- LangGraph Checkpointer：`max_size(5)`
- **理论最大：19 个连接**
- **实际观测：25 个连接**
- **差值：6 个泄漏连接**

---

## 根本原因（第一性原理分析）

### 公理 1：psycopg AsyncConnectionPool 的 Fork 不安全性

**来源**：psycopg_pool 官方文档

> Connection pools are **not fork-safe**. After a `fork()`, all the connections in the child process are **broken** and should not be used. The pool object in the child should be **discarded** and a new pool created.

**物理原因**：

1. **文件描述符共享**：
   - 连接池内部使用 socket 文件描述符 (FD)
   - `fork()` 后，父子进程的 FD 指向同一个内核 socket 对象
   - 多个进程同时读写会导致数据包错乱和连接状态不一致

2. **事件循环失效**：
   - asyncio 事件循环是进程级单例
   - `fork()` 后，子进程的事件循环是全新对象
   - 父进程连接池中的连接对象引用的是父进程的事件循环
   - 子进程中使用这些连接会导致 `RuntimeError: Event loop is closed`

3. **连接池状态错乱**：
   - 连接池的内部状态（可用连接数、引用计数等）在 fork 后不一致
   - 父子进程同时操作连接池会导致资源泄漏

### 公理 2：Python 类变量的继承语义

**OrchestratorFactory 的设计**：

```python
class OrchestratorFactory:
    _initialized: bool = False  # 类变量
    _connection_pool: AsyncConnectionPool | None = None  # 类变量
```

**fork() 后的内存状态**：

1. **父进程**初始化：
   ```python
   _initialized = True
   _connection_pool = <Pool 对象>
   _process_id = None  # 未跟踪进程 ID
   ```

2. **fork() 创建子进程**：
   - 子进程内存是父进程的**完整副本**（Copy-on-Write）
   - 子进程的类变量：`_initialized = True`（继承自父进程）

3. **子进程调用 `initialize()`**：
   ```python
   if cls._initialized:  # ← True（继承自父进程）
       return  # ← 提前返回！
   ```

4. **逻辑断裂点**：
   - 子进程使用继承的 `_connection_pool` 对象
   - 但连接池内部连接已失效（违反公理 1）

### 因果推导链

```
1. FastAPI 主进程启动
   └─> OrchestratorFactory.initialize()
       └─> _initialized = True
       └─> _connection_pool = AsyncConnectionPool(max_size=5)

2. Celery Worker 启动，fork 4 个子进程
   └─> os.fork() × 4
       └─> 每个子进程继承 _initialized = True
       └─> 每个子进程继承 _connection_pool 对象引用

3. 子进程初始化钩子执行
   └─> worker_process_init()
       └─> OrchestratorFactory.initialize()
           └─> if cls._initialized: return  # ← 提前返回！
           └─> 子进程使用继承的连接池（已失效）

4. 子进程执行任务
   └─> graph.aget_state(config)
       └─> checkpointer.aget_tuple()
           └─> pool.getconn(timeout=120)
               └─> 连接失效，无法获取新连接
               └─> 等待 120 秒后抛出 PoolTimeout

5. 连接泄漏累积
   └─> 失效的连接占用连接池槽位
   └─> 4 个子进程 × 5 个连接 = 20 个潜在泄漏
   └─> 加上主进程连接，总数超过 25 个
```

## 解决方案

### 修复 1：在 `OrchestratorFactory.initialize()` 中添加 Fork 检测

**文件**：`backend/app/core/orchestrator_factory.py`

**关键改动**：

1. **添加进程 ID 跟踪**：
   ```python
   class OrchestratorFactory:
       _process_id: int | None = None  # ✅ 新增
   ```

2. **Fork 检测逻辑**：
   ```python
   async def initialize(cls) -> None:
       import os
       current_pid = os.getpid()
       
       # ✅ 检测 1：如果进程 ID 改变，说明发生了 fork
       if cls._process_id is not None and cls._process_id != current_pid:
           logger.warning(
               "orchestrator_factory_fork_detected",
               parent_pid=cls._process_id,
               child_pid=current_pid,
           )
           
           # 清理父进程的资源引用（避免跨进程使用）
           cls._state_manager = None
           cls._checkpointer = None
           cls._connection_pool = None
           cls._agent_factory = None
           cls._initialized = False
           cls._process_id = None
       
       # ✅ 检测 2：如果已初始化且在同一进程，直接返回
       if cls._initialized and cls._process_id == current_pid:
           return
       
       # ... 正常初始化逻辑 ...
       
       cls._initialized = True
       cls._process_id = current_pid  # ✅ 保存当前进程 ID
   ```

3. **cleanup 方法重置进程 ID**：
   ```python
   async def cleanup(cls) -> None:
       # ...
       cls._process_id = None  # ✅ 重置
   ```

### 修复 2：简化 `worker_process_init` 中的逻辑

**文件**：`backend/app/core/celery_app.py`

**原逻辑（重复且复杂）**：
```python
# 关闭父进程的连接池
if OrchestratorFactory._connection_pool:
    loop.run_until_complete(OrchestratorFactory._connection_pool.close())

# 重置所有单例对象
OrchestratorFactory._initialized = False
OrchestratorFactory._connection_pool = None
# ...

# 重新初始化
loop.run_until_complete(OrchestratorFactory.initialize())
```

**新逻辑（简洁且正确）**：
```python
# ✅ 直接调用 initialize()，内部会自动处理 fork 检测
loop.run_until_complete(OrchestratorFactory.initialize())
```

## 技术债务与未来改进

### 1. 连接池配置优化

**当前问题**：
- LangGraph Checkpointer 的 `max_size=5` 可能在高并发场景下不足
- `timeout=120` 秒过长，会延迟错误检测

**建议改进**：
```python
# 根据 Celery Worker 并发数动态调整
worker_concurrency = settings.CELERY_WORKER_CONCURRENCY or 4
langgraph_max_size = max(5, worker_concurrency * 2)  # 每个并发 2 个连接

# 缩短超时，快速失败
timeout = 30  # 30 秒超时
```

### 2. 连接池监控与告警

**当前问题**：
- 缺少主动监控连接池使用率
- 泄漏问题难以及时发现

**建议改进**：
- 启用 Prometheus 监控（已实现，需确保启用）
- 添加 Grafana 告警规则：
  ```yaml
  - alert: DatabaseConnectionPoolHighUsage
    expr: db_pool_connections_in_use / (db_pool_size + db_max_overflow) > 0.8
    for: 5m
    annotations:
      summary: "数据库连接池使用率过高"
  ```

### 3. 进程管理改进

**当前问题**：
- 依赖 Celery prefork 模式，复杂度高
- Fork 安全性需要手动保证

**建议改进**：
- 考虑使用 Celery solo pool（单进程）或 gevent pool
- 或使用 Kubernetes + 单进程容器架构，避免 fork 问题

## 总结

**根本原因**：
- `OrchestratorFactory` 使用类变量存储连接池引用
- Celery Worker fork 后，子进程继承父进程的 `_initialized = True` 标志
- 导致子进程跳过重新初始化，使用失效的连接池

**核心修复**：
- 在 `initialize()` 中添加进程 ID 跟踪和 Fork 检测
- 自动检测进程 ID 变化，强制重新初始化
- 确保每个进程使用独立的连接池

**验证结果**：
- Fork 检测日志应该出现在 Worker 启动时
- 数据库连接数应该稳定在合理范围（< 100）
- 不再出现 `PoolTimeout` 错误

**未来改进**：
- 优化连接池配置参数
- 启用监控和告警
- 考虑更简单的进程管理架构
