# 内容生成测试脚本说明

## 概述

`test_content_generation.py` 是一个专门用于测试路线图内容生成流程的脚本，它会跳过前期的意图分析、课程设计、验证和人工审核等步骤，直接测试内容生成阶段（即路线图生成流程的后半段，`human_review` 通过后的部分）。

## 功能特性

### 1. Mock 模式（快速测试）
- 自动创建一个简化的路线图框架（2个Stage、2个Module、3个Concept）
- 适合快速验证内容生成流程是否正常工作
- 测试完成后可自动清理数据

### 2. 现有路线图模式
- 使用已存在的路线图进行测试
- 需要确保路线图包含完整的 `framework` 数据
- 支持限制生成的 Concept 数量（`--max-concepts`），加快测试速度

### 3. 完整的测试流程
1. **准备阶段**：创建或加载路线图数据
2. **执行阶段**：调用内容生成子图
3. **验证阶段**：检查生成结果和数据库记录
4. **清理阶段**（可选）：删除测试数据

## 使用方法

### 基本用法

```bash
cd backend

# Mock 模式（推荐用于快速测试）
uv run python scripts/test_content_generation.py --mock

# 使用现有路线图
uv run python scripts/test_content_generation.py --roadmap-id <roadmap_id>

# 限制生成数量（加快测试）
uv run python scripts/test_content_generation.py --roadmap-id <roadmap_id> --max-concepts 2

# 不清理测试数据
uv run python scripts/test_content_generation.py --mock --no-cleanup
```

### 命令行参数

| 参数 | 说明 | 示例 |
|------|------|------|
| `--mock` | 使用 Mock 路线图数据（快速测试） | `--mock` |
| `--roadmap-id` | 使用现有路线图的 ID | `--roadmap-id roadmap_abc123` |
| `--max-concepts` | 最多生成的 Concept 数量 | `--max-concepts 2` |
| `--no-cleanup` | 测试完成后不清理数据 | `--no-cleanup` |

## Mock 路线图结构

Mock 模式创建的路线图包含以下结构：

```
基础阶段 (S-1)
└── 入门模块 (M-1-1)
    ├── Python 基本语法 (C-1-1-1)
    └── 数据结构基础 (C-1-1-2)

进阶阶段 (S-2)
└── 进阶模块 (M-2-1)
    └── 面向对象编程 (C-2-1-1)
```

**总计**：
- 2 个 Stage
- 2 个 Module
- 3 个 Concept
- 总学时：7.0 小时

## 测试流程详解

### 1. 准备阶段

**Mock 模式**：
```python
# 创建 Mock 路线图框架
framework = create_mock_framework()

# 保存到数据库
roadmap_id, task_id = await create_mock_roadmap(user_id)
```

**现有路线图模式**：
```python
# 加载现有路线图
user_id, framework = await load_existing_roadmap(roadmap_id)

# 创建任务记录
task_id = await create_task_for_roadmap(roadmap_id, user_id)
```

### 2. 执行阶段

```python
# 提取 Concepts
concepts = extract_concepts_from_framework(framework, max_concepts)

# 执行内容生成
result = await run_content_generation(
    roadmap_id=roadmap_id,
    task_id=task_id,
    concepts=concepts,
)
```

**内容生成子图架构**：
```
外层 Fan-Out
    ↓
[并行] 为每个 Concept 创建子图实例
    ↓
单 Concept 子图（每个 Concept 独立）
    ↓
    内层 Fan-Out
        ↓
    [并行] Tutorial | Resource | Quiz
        ↓
    Fan-In（保存元数据）
    ↓
[汇总] 外层 Reduce
    ↓
最终汇总（更新 Framework）
```

### 3. 验证阶段

**生成结果统计**：
```
生成成功统计:
   - Tutorial: 3/3
   - Resource: 3/3
   - Quiz: 3/3
   - 元数据已保存: 3/3
```

**数据库记录验证**：
- Tutorial 记录数
- Resource 记录数
- Quiz 记录数
- Framework 更新状态

### 4. 清理阶段（可选）

```python
# 删除路线图（级联删除相关内容）
await roadmap_crud.delete_roadmap(session, roadmap_id)

# 删除任务记录
await task_crud.delete_task(session, task_id)
```

## 技术实现细节

### 1. 双 Checkpointer 架构

内容生成子图使用独立的 checkpointer，实现细粒度的状态管理：

```python
# 子图专用 checkpointer（独立于父图）
child_checkpointer = orchestrator_factory.build_child_checkpointer()
subgraph = build_content_generation_subgraph(checkpointer=child_checkpointer)

# 执行时共享 thread_id，但使用不同的命名空间
config = {
    "configurable": {
        "thread_id": task_id,
        "checkpoint_ns": "child_graph",  # 子图命名空间
        "runtime_context": runtime_context,
    }
}
```

### 2. RuntimeContext 上下文

提供统一的运行时上下文，包括状态管理、通知服务和日志记录：

```python
runtime_context = RuntimeContext(
    state_manager=state_manager,
    notification_service=notification_service,
    execution_logger=execution_logger,
)
```

### 3. Concept 上下文信息

为每个 Concept 添加 Stage 和 Module 信息，用于生成时的参考：

```python
for stage in framework.stages:
    for module in stage.modules:
        for concept in module.concepts:
            concept.stage_name = stage.name
            concept.module_name = module.name
            concepts.append(concept)
```

## 常见问题

### Q1: 如何获取现有路线图的 ID？

**方法1**：从数据库查询
```sql
SELECT roadmap_id, title, user_id 
FROM roadmap_metadata 
WHERE framework_data IS NOT NULL
ORDER BY created_at DESC 
LIMIT 10;
```

**方法2**：使用 API
```bash
# 需要先登录获取 token
curl -X GET "http://localhost:8000/api/v1/users/{user_id}/roadmaps" \
  -H "Authorization: Bearer {token}"
```

### Q2: 为什么要限制 Concept 数量？

- **加快测试**：生成内容需要调用 LLM，3个 Concept 通常需要 30-60 秒
- **验证流程**：测试流程是否正常，2-3 个 Concept 就足够了
- **调试问题**：减少生成数量可以更快定位问题

### Q3: Mock 模式和现有路线图模式的区别？

| 特性 | Mock 模式 | 现有路线图模式 |
|------|-----------|----------------|
| 数据来源 | 自动创建简化框架 | 使用已存在的路线图 |
| 适用场景 | 快速验证流程 | 测试真实数据 |
| 数据清理 | 默认自动清理 | 默认不清理 |
| Concept 数量 | 固定 3 个 | 可自定义 |

### Q4: 如何保留测试数据供后续查看？

使用 `--no-cleanup` 参数：

```bash
uv run python scripts/test_content_generation.py --mock --no-cleanup
```

测试完成后，脚本会显示路线图 ID，可以通过 API 或数据库查看生成的内容。

## 故障排查

### 问题1: "路线图缺少 framework 数据"

**原因**：使用的路线图尚未完成课程设计阶段

**解决方案**：
1. 使用 `--mock` 模式
2. 或确保路线图已完成 `curriculum_design` 和 `validation` 阶段

### 问题2: "Celery Session 连接池错误"

**原因**：跨进程使用数据库连接

**解决方案**：
- 脚本已使用 `get_celery_session()` 解决此问题
- 如果仍有问题，检查 `app/db/celery_session.py` 配置

### 问题3: "LLM 调用超时或失败"

**原因**：
- 网络问题
- API Key 无效
- LLM 服务不可用

**解决方案**：
1. 检查 `.env` 配置
2. 验证 API Key 有效性
3. 查看日志文件 `backend/logs/err.log`
