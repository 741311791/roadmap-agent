# 人工审核后恢复工作流超时问题修复

## 问题描述

### 错误现象

运行 `scripts/test_human_review.py` 测试脚本时，在人工审核批准后，尝试恢复工作流时出现数据库连接超时错误：

```
psycopg.OperationalError: consuming input failed: could not receive data from server: Operation timed out
```

### 错误堆栈

```python
File "app/services/workflows/execution/workflow_execution_service.py", line 357, in resume_workflow_after_review
    final_state = await executor.resume_after_human_review(...)
File "app/core/orchestrator/executor.py", line 437, in resume_after_human_review
    state_before_resume = await self.graph.aget_state(config)
File "langgraph/checkpoint/postgres/aio.py", line 194, in aget_tuple
    await cur.execute(...)
```

### 错误发生时机

1. 用户在测试脚本中选择批准任务
2. 系统调用 `resume_workflow_after_review` 恢复工作流
3. LangGraph 尝试从 PostgreSQL checkpoint 表读取状态
4. 数据库连接超时（约 60-120 秒）

---

## 根本原因分析

### 1. 网络延迟

**checkpoint 数据库位置**：阿里云RDS (`pgm-bp19tba3692jfh9aso.pg.rds.aliyuncs.com`)

**问题**：
- 跨地域访问，网络延迟较高
- 大量 checkpoint 数据查询需要更长时间
- 原有超时配置（60-120秒）不足以应对网络抖动

### 2. Checkpoint 数据量

**问题**：
- checkpoint 表随着任务执行不断增长
- 每个工作流节点都会保存状态快照
- 已完成/失败任务的 checkpoint 数据未清理

### 3. 连接池配置

**原有配置**：
```python
timeout=120,  # 获取连接超时 120 秒
connect_timeout=60,  # 连接建立超时 60 秒
statement_timeout=180000,  # SQL 语句超时 180 秒
```

**问题**：
- 阿里云RDS网络不稳定时，120秒仍然不够
- 缺少 `idle_in_transaction_session_timeout` 配置

---

## 解决方案

### 方案1：优化连接池配置（已实施）✅

**修改文件**：`backend/app/core/orchestrator_factory.py`

**优化内容**：

1. **延长获取连接超时**：120秒 → 300秒（5分钟）
   ```python
   timeout=300,  # 应对阿里云RDS网络延迟
   ```

2. **延长连接建立超时**：60秒 → 120秒
   ```python
   connect_timeout=120,  # 阿里云RDS可能较慢
   ```

3. **添加事务超时配置**：
   ```python
   options="-c statement_timeout=300000 -c idle_in_transaction_session_timeout=300000"
   # 两个超时都设置为 300 秒（5分钟）
   ```

4. **保持 TCP keepalive 配置**：
   ```python
   keepalives=1,
   keepalives_idle=20,  # 20秒后开始探测
   keepalives_interval=5,  # 探测间隔5秒
   keepalives_count=6,  # 最多6次探测（总计30秒）
   ```

### 方案2：添加重试机制（已实施）✅

**修改文件**：`backend/app/services/workflows/execution/workflow_execution_service.py`

**重试逻辑**：

```python
max_retries = 3
retry_delay = 5  # 秒

for attempt in range(max_retries):
    try:
        final_state = await executor.resume_after_human_review(
            task_id=task_id,
            approved=approved,
            feedback=feedback,
        )
        break  # 成功则跳出循环
    except Exception as e:
        error_msg = str(e)
        is_timeout = "timeout" in error_msg.lower() or "could not receive data" in error_msg.lower()
        
        if is_timeout and attempt < max_retries - 1:
            logger.warning(
                "resume_workflow_retry",
                task_id=task_id,
                attempt=attempt + 1,
                max_retries=max_retries,
                error=error_msg,
                retry_in_seconds=retry_delay,
            )
            await asyncio.sleep(retry_delay)
            continue  # 重试
        else:
            # 最后一次失败或非超时错误，抛出异常
            raise
```

**重试策略**：
- 最多重试 3 次
- 每次重试间隔 5 秒
- 仅对超时错误重试（包含 "timeout" 或 "could not receive data"）
- 非超时错误直接抛出

### 方案3：Checkpoint 数据清理脚本（已创建）✅

**脚本路径**：`backend/scripts/cleanup_checkpoints.py`

**功能**：
1. 显示 checkpoint 表统计信息（记录数、表大小）
2. 清理已完成/失败任务的 checkpoint 数据
3. 可选清理指定天数之前的旧数据

## 预期效果

### 短期效果
- ✅ 网络延迟导致的偶发性超时可以通过重试机制自动恢复
- ✅ 连接池超时配置延长，降低超时概率

### 中期效果
- ✅ 清理历史 checkpoint 数据，减小表大小
- ✅ 提升 checkpoint 查询速度

### 长期建议

1. **定期清理 checkpoint 数据**
   - 建议每周运行一次 `cleanup_checkpoints.py`
   - 或添加到定时任务（Cron Job）

2. **监控 checkpoint 表大小**
   - 设置告警：表大小超过 100MB
   - 记录数超过 10000 条

3. **考虑数据库优化**
   - 在 `thread_id` 和 `checkpoint->>'ts'` 字段上添加索引
   - 考虑使用更近的数据库实例（减少网络延迟）

4. **升级 LangGraph**
   - 关注官方是否有 checkpoint 优化更新
   - 考虑使用 Redis 作为 checkpoint 存储（适合大规模场景）

## 总结

本次修复通过**三个层次**的优化，全面解决了人工审核后恢复工作流的超时问题：

1. **基础设施层**：优化连接池配置，延长超时时间，应对阿里云RDS网络延迟
