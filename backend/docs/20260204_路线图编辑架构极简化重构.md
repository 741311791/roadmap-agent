# 路线图编辑架构极简化重构

**日期**: 2026-02-04  
**类型**: 架构简化  
**影响范围**: EditPlanAnalyzer, RoadmapEditor, 数据模型

## 重构背景

第二版架构（Stage 级别 + 并行处理）虽然降低了复杂度，但仍存在过度工程化的问题：
- 依赖关系管理（dependencies）
- 并行执行策略（execution_strategy）
- 保留要求（preservation_requirements）
- StageProcessor 的复杂并行逻辑（500+ 行代码）

这些设计增加了维护成本，但并未充分发挥 LLM 的能力。

## 核心改进

### 1. 移除过度设计

删除的字段和逻辑：
- `StageEditTask.dependencies` - 依赖关系
- `StageEditTask.order` - 插入顺序
- `EditPlan.execution_strategy` - 执行策略
- `EditPlan.preservation_requirements` - 保留要求
- `StageProcessor` 整个文件（565 行）

### 2. 采用两阶段生成

效仿 IntentAnalyzerAgent 的成功模式：
- 第一阶段：LLM 思考如何修改（思维链）
- 第二阶段：提取结构化的 RoadmapFramework

### 3. LLM 生成修改总结

从自动生成改为 LLM 生成：
- 更准确地描述修改内容
- 更符合人类阅读习惯

## 架构对比

### 第二版（复杂）

```
EditPlan (tasks + strategy + preservation)
  ↓
StageProcessor (依赖分析 + 并行执行)
  ↓
多个 LLM 调用（每个 Stage 一个）
  ↓
合并结果
  ↓
FrameworkDiff
  ↓
自动生成总结
```

### 第三版（极简）

```
EditPlan (只有 tasks)
  ↓
RoadmapEditor (两阶段生成)
  ↓
单个 LLM 调用（理解所有 tasks）
  ↓
FrameworkDiff
  ↓
LLM 生成总结
```

```python
async def execute(input_data: RoadmapEditInput) -> RoadmapEditOutput:
    # 1. 两阶段生成新框架
    updated_framework = await self._call_llm(
        messages,
        response_model=RoadmapFramework,
        use_two_stage=True,

        old_framework, updated_framework, tasks
    )
    
    return RoadmapEditOutput(...)
```

## 核心优势

### 1. 代码量大幅减少

- 删除 StageProcessor (565 行)
- 简化数据模型（13 行字段）
- 简化 Prompt（50+ 行）
- **净减少约 600+ 行代码**

### 2. 逻辑更清晰

之前：
```
EditPlan → 依赖分析 → 拓扑排序 → 并行执行 → 合并结果 → ...
```

现在：
```
EditPlan → 两阶段生成 → 对比 → 总结
```

### 3. 充分发挥 LLM 能力

- LLM 可以理解所有 tasks 的整体意图
- 自动判断修改顺序、保留内容
- 生成更自然的修改总结

### 4. 更容易维护

- 减少了 StageProcessor 的复杂状态管理
- 减少了并行执行的调试难度
- 减少了依赖关系的理解成本

## 关键设计决策

### 为什么移除并行处理？

**之前的假设**: 不同 Stage 的修改可以并行执行，提升性能

**实际情况**:
- 并行带来的复杂度 >> 性能提升
- 大部分场景只修改 1-2 个 Stage
- LLM 理解整体意图比分散处理更准确

**结论**: 用 LLM 的整体理解能力替代工程化的并行逻辑

### 为什么移除依赖关系？

**之前的假设**: 需要显式标注 Stage 之间的依赖关系

**实际情况**:
- LLM 可以自己理解前后关系
- 大部分修改不需要严格的顺序
- 依赖关系增加了 Prompt 的复杂度

**结论**: 让 LLM 自己判断修改顺序

### 为什么使用 LLM 生成总结？

**之前的做法**: 自动统计变更（"新增 X 个，删除 Y 个"）

**问题**:
- 机械化的统计不够人性化
- 无法准确描述修改意图

**改进**: LLM 生成的总结示例
- ✅ "简化阶段2，删除Flask高级特性，总时长减少8小时。"
- ✅ "移除了 Stage 3，路线图精简为 2 个阶段，总时长从 90h 降至 34h。"
- ✅ "精简阶段2和3，删除高级特性与ORM，总时长由90h降至76h。"

## 总结

本次重构通过移除过度工程化的设计，大幅简化了代码和逻辑，同时充分发挥了 LLM 的语义理解能力。核心理念是：**简单往往更有效，让 LLM 做它擅长的事（理解语义、整体思考），而不是用工程化的方式限制它。**

测试结果证明，简化后的架构：
- ✅ 功能完全正常
- ✅ 修改总结更准确
- ✅ 代码更易维护
- ✅ 删除了 600+ 行复杂代码

**核心优势**: 用 LLM 的智能替代工程化的复杂性。
