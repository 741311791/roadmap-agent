# API速率限制全局中间件设计方案

## 一、问题背景

### 1.1 问题描述
在内容生成阶段，系统会并发调用多个API（OpenAI、Anthropic、Tavily等），导致频繁触发API厂商的速率限制（HTTP 429错误）。

### 1.2 根本原因
- API厂商按**IP地址**识别请求来源
- 厂商设置了**RPM限制**（Requests Per Minute，每分钟请求数）
- 系统内部的并发控制（如Celery concurrency）无法感知全局速率
- 多个Worker/进程共享同一IP，但各自独立计数，导致合计超限

### 1.3 设计目标
1. **全局速率控制**：所有进程/Worker共享速率限制，防止IP级别超限
2. **透明集成**：无需修改现有Agent代码，自动生效
3. **优雅降级**：超限时自动等待，而非直接拒绝或报错
4. **可观测性**：提供监控接口，查看各API的使用情况和等待统计
5. **配置化管理**：支持环境变量配置不同Provider的RPM限制

### 2.2 滑动窗口算法

使用Redis ZSET实现精确的滑动窗口计数：

```python
# Redis Key格式
rate_limit:openai -> ZSET {
    "1738368000.123:task_1": 1738368000.123,
    "1738368001.456:task_2": 1738368001.456,
    ...
}

# 工作流程
1. 清理60秒前的旧记录：ZREMRANGEBYSCORE rate_limit:openai -inf <now-60>
2. 统计当前窗口内请求数：ZCARD rate_limit:openai
3. 判断是否超限：current_count < limit
4. 如果未超限：记录本次请求 ZADD rate_limit:openai <now> <request_id>
5. 如果超限：计算等待时间并sleep
```

**优势**：
- 精确控制：每秒都是独立的窗口，不会出现固定窗口的"边界问题"
- 自动过期：通过EXPIRE设置Key过期时间（70秒），自动清理
- 高性能：Redis原子操作，支持高并发

### 3.2 核心类：APIRateLimiter

**文件**：`backend/app/core/rate_limiter.py`

**关键方法**：
1. `acquire(provider: str)` - 获取API调用许可，超限时自动等待
2. `get_current_usage(provider: str)` - 查询当前速率使用情况
3. `get_all_usage()` - 查询所有Provider的使用情况
4. `get_stats()` - 获取统计信息（总请求数、等待次数、等待时长）
5. `reset_provider(provider: str)` - 重置某个Provider的速率限制

**支持的Provider**：
- `openai` - OpenAI API
- `anthropic` - Anthropic Claude API
- `deepseek` - DeepSeek API
- `tavily` - Tavily Search API

### 3.3 BaseAgent集成

**修改点**：
```python
# backend/app/agents/base.py

async def _call_llm(...):
    # ⭐ 调用LLM前，获取速率限制许可
    await self.rate_limiter.acquire(self.model_provider)
    
    # 原有的LLM调用逻辑
    response = await litellm.acompletion(...)
    ...

async def _call_llm_stream(...):
    # ⭐ 流式调用同样需要获取许可
    await self.rate_limiter.acquire(self.model_provider)
    
    # 原有的流式调用逻辑
    ...
```

**集成优势**：
- 所有继承`BaseAgent`的Agent自动受保护
- 对现有Agent代码零侵入
- 统一的速率控制点，便于维护

## 四、部署指南

### 4.1 配置步骤

1. **更新环境变量**（.env）：
```bash
# 根据实际API套餐配置RPM限制
OPENAI_RPM_LIMIT=60
ANTHROPIC_RPM_LIMIT=50
DEEPSEEK_RPM_LIMIT=60
TAVILY_RATE_LIMIT_PER_MINUTE=100
```

2. **确保Redis可用**：
   - 速率限制器依赖Redis存储
   - 检查`REDIS_URL`配置正确
   - 测试Redis连接：`redis-cli ping`

3. **重启服务**：
```bash
# 重启FastAPI
uvicorn app.main:app --reload

# 重启Celery Workers
celery -A app.core.celery_app worker --loglevel=info
```

### 4.2 验证部署

1. **检查速率限制器初始化**：
```bash
# 查看日志，应该看到类似输出：
# rate_limiter_initialized rpm_limits={'openai': 60, 'anthropic': 50, ...}
```

2. **测试API调用**：
   - 发起路线图生成任务
   - 观察日志中的速率限制信息：
     - `rate_limiter_acquired` - 成功获取许可
     - `rate_limiter_waiting` - 超限等待

3. **查看监控接口**：
```bash
# 查询所有API速率使用情况
curl -H "Authorization: Bearer <admin_token>" \
  http://localhost:8000/api/v1/admin/monitoring/api-rate-limits

# 查询OpenAI速率使用情况
curl -H "Authorization: Bearer <admin_token>" \
  http://localhost:8000/api/v1/admin/monitoring/api-rate-limits/openai
```

### 4.3 调优建议

1. **设置RPM限制为厂商限制的80%**：
   - 留出安全余量，避免临界超限
   - 例如：OpenAI免费用户60 RPM → 设置为48

2. **根据并发度调整**：
   - Celery concurrency=20 → RPM应设置为 `20 * 预期每分钟任务数`
   - 如果经常看到`rate_limiter_waiting`，说明RPM设置过低

3. **监控等待时长**：
   - 如果`total_wait_seconds`持续增长，考虑：
     - 增加API配额（升级套餐）
     - 降低Celery并发度
     - 优化Agent Prompt减少Token消耗

## 五、错误处理

### 5.1 优雅降级策略

**Redis连接失败**：
```python
# 速率限制器异常时，自动降级：允许请求通过
try:
    await rate_limiter.acquire(provider)
except Exception as e:
    logger.warning("rate_limiter_degraded", error=str(e))
    # 继续执行，不阻塞业务
```

**不支持的Provider**：
```python
# 如果Provider不在配置中，直接放行（不限制）
if provider not in self.rpm_limits:
    logger.warning("rate_limiter_unsupported_provider", provider=provider)
    return  # 优雅降级
```

### 5.2 日志监控

**关键日志事件**：
- `rate_limiter_initialized` - 初始化成功
- `rate_limiter_acquired` - 成功获取许可
- `rate_limiter_waiting` - 超限等待（⚠️ 需关注）
- `rate_limiter_error` - 速率限制器异常（🚨 需告警）
- `rate_limiter_degraded` - 降级处理（⚠️ 需关注）

**告警规则**（推荐）：
- `rate_limiter_error` 出现 → 立即告警
- `rate_limiter_waiting` 频率过高 → 告警（考虑扩容API配额）
- `rate_limiter_degraded` 出现 → 告警（Redis可能故障）

## 七、常见问题

### Q1: 为什么选择Redis而非内存计数？
**A**: 
- 多进程/多Worker场景下，内存计数无法共享
- Redis提供原子操作，保证并发安全
- Redis支持ZSET高效实现滑动窗口

### Q2: 会不会影响性能？
**A**:
- Redis操作延迟通常<1ms，对API调用（秒级）影响可忽略
- 等待时使用`asyncio.sleep()`，不阻塞事件循环
- 只有超限时才等待，正常情况下无性能损耗

### Q3: 如何处理突发流量？
**A**:
- 滑动窗口算法支持突发：只要60秒内不超限即可
- 可临时提高RPM限制应对突发（修改.env后重启）
- 考虑使用Token Bucket算法支持"允许短时突发"（未来优化）

### Q4: 如何监控速率限制效果？
**A**:
- 查看监控接口：`/api/v1/admin/monitoring/api-rate-limits`
- 观察日志中的`rate_limiter_waiting`频率
- 检查`total_wait_seconds`累计值
- 对比部署前后的429错误率

### Q5: 是否支持动态调整RPM限制？
**A**:
- 当前版本：修改.env后需重启服务
- 未来优化：可支持热更新（通过Redis存储配置）

### Q6: Tavily频繁报429错误怎么办？
**A**:
- **检查Key类型**：开发Key (`tvly-dev-*`) 速率限制极低（~5-10 RPM），建议使用生产Key
- **降低速率限制**：修改 `TAVILY_RATE_LIMIT_PER_MINUTE=5`（开发环境）
- **查看监控**：访问 `/api/v1/admin/monitoring/api-rate-limits/tavily` 查看实时使用情况
- **检查并发**：如果Celery concurrency过高，考虑降低或增加Key数量
- **错误日志示例**：
  ```
  UsageLimitExceededError: 'Your request has been blocked due to excessive requests. 
  Please reduce the rate of requests. Verify you are using production API keys.'
  ```

## 九、总结

本方案通过**全局速率限制器**解决了内容生成阶段API超限的问题，具有以下特点：

✅ **全局控制**：多进程共享速率限制，防止IP级别超限  
✅ **透明集成**：BaseAgent自动集成，无需修改现有代码  
✅ **优雅等待**：超限时自动等待，而非直接失败  
✅ **可观测性**：提供监控接口，实时查看速率使用情况  
✅ **配置化**：支持环境变量配置，便于不同环境调整  
✅ **高性能**：基于Redis滑动窗口，支持高并发  

部署后，系统将能够有效避免API速率超限问题，提升内容生成的稳定性和成功率。
