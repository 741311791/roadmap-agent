### 2. 数据库连接池耗尽风险

**问题描述**:  
虽然实现了连接池监控，但未见主动的连接泄漏预防机制。在 `session.py` 中发现临界使用率警告 (90%)，但缺乏自动降级或限流机制。

**位置**:
```python
# backend/app/db/session.py:108-114
if usage_ratio > 0.9:
    logger.error(
        "db_pool_critical_usage",
        usage_ratio=round(usage_ratio * 100, 1),
        message=f"🚨 连接池使用率过高 ({round(usage_ratio * 100, 1)}%)，即将耗尽",
    )
```

**影响等级**: 🔴 **严重 (Critical)**  
- 可能导致请求挂起或超时
- 高负载场景下服务不可用

**建议方案**:
```python
# 增强版连接池保护
from contextlib import asynccontextmanager

@asynccontextmanager
async def safe_db_session():
    """带超时和降级的数据库会话"""
    pool_status = await get_pool_status()
    
    # 连接池使用率超过 85% 时触发限流
    if pool_status["usage_ratio"] > 85:
        logger.warning("db_pool_throttling_activated")
        await asyncio.sleep(0.5)  # 短暂降速
    
    # 超过 95% 拒绝非关键请求
    if pool_status["usage_ratio"] > 95:
        raise HTTPException(503, "服务暂时不可用，请稍后重试")
    
    async with async_session_maker() as session:
        yield session
```

### 3. Agent 配置回退链过于复杂

**问题描述**:  
多个 Agent 使用复杂的配置回退逻辑 (`getattr(settings, 'X_PROVIDER', None) or Y_PROVIDER`)，导致配置来源不透明，难以排查问题。

**位置**:
```python
# backend/app/agents/qa_agent.py:42-45
super().__init__(
    agent_id=agent_id,
    model_provider=model_provider or getattr(settings, 'QA_PROVIDER', None) or settings.GENERATOR_PROVIDER,
    model_name=model_name or getattr(settings, 'QA_MODEL', None) or settings.GENERATOR_MODEL,
    base_url=base_url or getattr(settings, 'QA_BASE_URL', None) or settings.GENERATOR_BASE_URL,
    api_key=api_key or getattr(settings, 'QA_API_KEY', None) or settings.GENERATOR_API_KEY,
    ...
)
```

**影响等级**: 🟠 **高 (High)**  
- 配置优先级不明确
- 难以调试"为什么使用了错误的模型"
- 增加新 Agent 时容易出错

**建议方案**:
```python
# 1. 在 Settings 中明确定义配置优先级
class Settings(BaseSettings):
    def get_agent_config(self, agent_name: str) -> dict:
        """
        获取 Agent 配置，带清晰的回退逻辑
        
        优先级: 
        1. {AGENT_NAME}_PROVIDER
        2. GENERATOR_PROVIDER
        """
        provider = getattr(self, f"{agent_name.upper()}_PROVIDER", None) or self.GENERATOR_PROVIDER
        model = getattr(self, f"{agent_name.upper()}_MODEL", None) or self.GENERATOR_MODEL
        
        logger.info(
            "agent_config_resolved",
            agent_name=agent_name,
            provider=provider,
            model=model,
            config_source="dedicated" if getattr(self, f"{agent_name.upper()}_PROVIDER", None) else "fallback"
        )
        
        return {
            "provider": provider,
            "model": model,
            "base_url": getattr(self, f"{agent_name.upper()}_BASE_URL", None) or self.GENERATOR_BASE_URL,
            "api_key": getattr(self, f"{agent_name.upper()}_API_KEY", None) or self.GENERATOR_API_KEY,
        }

# 2. Agent 初始化简化
class QAAgent(BaseAgent):
    def __init__(self, agent_id: str = "qa_agent", **overrides):
        config = settings.get_agent_config("qa")
        config.update(overrides)  # 允许覆盖
        super().__init__(agent_id=agent_id, **config)
```

### 8. 数据库模型时间处理的潜在时区混淆

**问题描述**:  
虽然文档说明使用"北京时间 (UTC+8)"，但实现中使用 `TIMESTAMP WITHOUT TIME ZONE`，存在时区混淆风险。

**位置**:
```python
# backend/app/models/database.py:22-36
BEIJING_TZ = timezone(timedelta(hours=8))

def beijing_now() -> datetime:
    # 获取UTC时间并转换为北京时间
    utc_time = datetime.now(timezone.utc)
    beijing_time = utc_time.astimezone(BEIJING_TZ)
    
    # ⚠️ 移除时区信息后存储
    return beijing_time.replace(tzinfo=None)
```

**问题分析**:
1. ✅ **优点**: 避免 PostgreSQL 自动转换为 UTC
2. ❌ **缺点**: 无法区分"无时区信息"和"北京时间"
3. ❌ **风险**: 跨时区部署时容易出错

**建议方案**:

**方案 A: 完全使用 UTC (推荐)**
```python
# 所有时间统一使用 UTC，前端负责本地化显示
def utc_now() -> datetime:
    """返回带时区信息的 UTC 时间"""
    return datetime.now(timezone.utc)

# 数据库字段
created_at: datetime = Field(
    default_factory=utc_now,
    sa_column=Column(DateTime(timezone=True))  # 存储时区信息
)
```

**方案 B: 明确标注时区 (当前方案改进)**
```python
# 在模型中添加注释
class RoadmapTask(SQLModel, table=True):
    """
    时间字段说明：
    - 所有时间字段存储为北京时间 (UTC+8)
    - 使用 TIMESTAMP WITHOUT TIMEZONE
    - 前端需自行处理时区转换
    """
    created_at: datetime = Field(...)
```
