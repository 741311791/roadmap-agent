# 数据库连接池跨进程污染修复 (20260114)

## 问题现象

执行 `scripts/test_roadmap_generation.py` 时，任务失败并报错：

```
ForeignKeyViolationError: insert or update on table "tutorial_metadata" violates foreign key constraint "tutorial_metadata_roadmap_id_fkey"
DETAIL: Key (roadmap_id)=(python-fullstack-engineer-b4k9m2n7) is not present in table "roadmap_metadata"
```

**矛盾点**：
- 日志显示 `curriculum_design` 节点"执行成功"
- 数据库中却没有对应的 `roadmap_id` 记录
- 后续 `fan_in_and_save` 节点插入 `tutorial_metadata` 时触发外键约束错误

---

## 根因分析

### 物理层面的逻辑断裂点

**核心原因**：在 **Celery Worker 进程** 中混用了两种不同的数据库引擎：

1. **FastAPI 应用引擎** (`app.db.session.async_session_maker`)
   - 使用连接池：`pool_size=20`, `max_overflow=10`
   - 设计目标：FastAPI 主进程的并发请求处理

2. **Celery 专用引擎** (`app.db.celery_session.get_celery_session`)
   - 使用 `NullPool`：每次创建新连接
   - 设计目标：避免跨进程连接池状态污染

### 因果推导链条

```
1. curriculum_design 节点完成
   ↓
2. Executor 调用 CurriculumDesignHandler
   → 使用 get_celery_session() (✅ NullPool)
   → 调用 roadmap_crud.save_roadmap_metadata()
   → session.flush() + 自动 commit
   ↓
3. 数据应该已持久化到 roadmap_metadata 表
   ↓
4. fan_in_and_save 节点执行
   → 使用 async_session_maker() (❌ ConnectionPool - 继承自父进程)
   → 尝试插入 tutorial_metadata
   ↓
5. 外键约束失败
   → 说明当前 Session 看不到 roadmap_metadata 记录
   ↓
6. 原因：跨进程连接池状态不同步
   → Celery Worker 子进程继承了 FastAPI 父进程的连接池引用
   → 连接状态混乱，事务可见性被破坏
```

### 公理违反

**公理1：进程隔离定律**
> Celery 使用 prefork 模式，子进程继承父进程的连接池引用会导致跨进程连接污染。

**公理2：事务可见性原则**
> 在同一数据库实例中，事务 A commit 后，事务 B 必须能看到 A 的修改（READ COMMITTED 隔离级别）。

---

## 修复方案

### 统一使用 Celery 专用 Session

**修复原则**：在 **Celery Worker 进程** 中运行的所有代码，必须使用 `get_celery_session()`。

### 修复文件列表

| 文件 | 修复点 | 修复内容 |
|---|---|---|
| `backend/app/core/orchestrator/subgraphs/single_concept_content_generation.py` | `fan_in_and_save` 节点 | `async_session_maker()` → `get_celery_session()` |
| `backend/app/core/orchestrator/subgraphs/content_generation.py` | `final_aggregation` 节点 | `async_session_maker()` → `get_celery_session()` |
| `backend/app/tasks/content_generation_tasks.py` | `generate_single_concept_content_task` | `async_session_maker()` → `get_celery_session()` |

#### 1. single_concept_content_generation.py


## 架构原理说明

### FastAPI Session vs Celery Session

| 特性 | FastAPI Session | Celery Session |
|---|---|---|
| 引擎 | `engine` (ConnectionPool) | `celery_engine` (NullPool) |
| 连接池 | `pool_size=20, max_overflow=10` | 无连接池，每次创建新连接 |
| 使用场景 | FastAPI 主进程的 HTTP 请求 | Celery Worker 子进程的异步任务 |
| 导入路径 | `from app.db.session import async_session_maker` | `from app.db.celery_session import get_celery_session` |
| Fork 安全性 | ❌ 不安全（跨进程状态共享） | ✅ 安全（独立连接） |

### 为什么需要 NullPool？

**问题场景**：
1. FastAPI 主进程创建连接池（20 个连接）
2. Celery Worker 通过 prefork 创建子进程
3. 子进程继承父进程的连接池引用（但不是连接本身）
4. 子进程尝试使用连接池 → 连接状态混乱 → 事务可见性被破坏

**NullPool 解决方案**：
- 每次请求都创建新连接，用完立即关闭
- 完全避免连接池状态的跨进程共享问题
- 性能略低（每次都要建立 TCP 连接），但在 Celery 场景下可接受

## 最佳实践总结

### 规则1：严格区分 Session 使用场景

```python
# ✅ FastAPI API 端点
from app.db.session import CurrentSession, CurrentSessionTransaction

@router.get("/roadmaps")
async def list_roadmaps(db: CurrentSession):
    ...

# ✅ Celery Task 和 LangGraph Node
from app.db.celery_session import get_celery_session

async with get_celery_session() as session:
    ...
```

### 规则2：子图内部必须使用 Celery Session

**错误示例**：
```python
# ❌ 错误：在子图中使用 FastAPI Session
from app.db.session import async_session_maker

async def fan_in_and_save(state, config):
    async with async_session_maker() as session:  # ❌ 跨进程污染
        ...
```

**正确示例**：
```python
# ✅ 正确：在子图中使用 Celery Session
from app.db.celery_session import get_celery_session

async def fan_in_and_save(state, config):
    async with get_celery_session() as session:  # ✅ 进程安全
        ...
```

### 规则3：Celery Task 必须使用 Celery Session

**错误示例**：
```python
# ❌ 错误：在 Celery Task 中使用 FastAPI Session
from app.db.session import async_session_maker

@celery_app.task
def my_task():
    async def execute():
        async with async_session_maker() as session:  # ❌ 跨进程污染
            ...
```

**正确示例**：
```python
# ✅ 正确：在 Celery Task 中使用 Celery Session
from app.db.celery_session import get_celery_session

@celery_app.task
def my_task():
    async def execute():
        async with get_celery_session() as session:  # ✅ 进程安全
            ...
```

## 总结

本次修复通过统一使用 `get_celery_session()`，彻底解决了 Celery Worker 进程中的数据库连接池跨进程污染问题。

**关键要点**：
1. **根因**：跨进程连接池状态共享 → 事务可见性被破坏
2. **方案**：Celery 环境统一使用 NullPool → 每次创建新连接
3. **规则**：FastAPI 用 `async_session_maker`，Celery 用 `get_celery_session()`
