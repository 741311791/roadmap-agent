# 技术栈测验题初始化异步化改造完成

## 问题背景

### 原有实现存在的问题

在 `backend/app/main.py` 中，应用启动时会**同步阻塞**生成技术栈测验题：

```python
# 启动时同步生成测验题（阻塞启动）
await initialize_tech_assessments()
```

**核心问题**：
1. **阻塞启动**：空白数据库需要生成 `6技术栈 × 3级别 = 18组题目`
2. **启动时间长**：每组题目需要多次LLM调用，加上防API限流的1秒延迟，总耗时可能达到 **2-5分钟**
3. **启动失败风险**：LLM服务不可用时，应用启动会延迟（虽然有异常捕获，但仍会等待超时）

---

## 解决方案：迁移到Celery异步任务

### 架构设计

```
应用启动 (FastAPI)
    ↓
触发 Celery 任务（不等待）
    ↓
返回启动完成
    ↓
Celery Worker 在后台并行生成题目
    ↓
前端可通过 API 查询进度
```

### 核心优势

1. ✅ **非阻塞启动**：应用启动时只触发任务，立即返回
2. ✅ **并行生成**：使用 Celery Group 并行生成18组题目，大幅缩短总耗时
3. ✅ **失败重试**：单个题目生成失败会自动重试3次（间隔60秒）
4. ✅ **进度监控**：提供API查询初始化进度
5. ✅ **手动补全**：支持手动触发初始化任务补全缺失题目

## 代码变更

### 1. 新增：Celery 异步任务模块

**文件**: `backend/app/tasks/assessment_initialization_tasks.py`

**核心任务**：

#### (1) `check_and_trigger_assessment_generation`
- 检查数据库中已有的题目
- 识别缺失的 (technology, level) 组合
- 并行触发所有缺失题目的生成任务

#### (2) `generate_single_assessment`
- 生成单个技术栈测验题目集
- 支持失败重试（最多3次，间隔60秒）
- 超时限制：30分钟硬超时，28分钟软超时

#### (3) `get_initialization_progress`
- 查询初始化进度
- 返回已完成数量和百分比

### 2. 修改：启动初始化逻辑

**文件**: `backend/app/services/learning/assessment_initializer.py`

**改造前**（同步阻塞）：
```python
async def initialize_tech_assessments():
    # 循环生成每组题目（阻塞）
    for tech, level in missing_combinations:
        assessment_data = await generator.generate_assessment_with_plan(tech, level)
        await tech_crud.create_assessment(...)
        await asyncio.sleep(1)  # 防API限流
```

**改造后**（触发异步任务）：
```python
async def initialize_tech_assessments():
    # 只触发Celery任务，不等待完成
    task = check_and_trigger_assessment_generation.apply_async()
    return {
        "status": "triggered",
        "task_id": task.id,
        "success": True,
    }
```

## 注意事项

### 1. Celery Worker 必须启动
异步任务需要 Celery Worker 才能执行，确保以下命令在独立终端运行：
```bash
make celery
```

### 2. Redis 必须可用
Celery 依赖 Redis 作为消息队列，确保 Redis 服务运行正常：
```bash
redis-cli ping  # 应返回 PONG
```

### 3. litellm Event Loop 隔离修复
已在 `celery_app.py` 的 `worker_process_init` 钩子中添加 litellm 状态重置逻辑，解决 Celery fork 模式下的 asyncio.Queue 跨 event loop 污染问题。

**根本原因**：
- litellm 在模块导入时创建全局 `asyncio.Queue`
- Celery fork 子进程继承此 Queue，但它绑定到父进程的 event loop
- 子进程创建新 event loop 后，访问旧 Queue 导致 `RuntimeError`

**修复方案**：
- 在每个 Worker 子进程初始化时重置 litellm 全局状态
- 强制 litellm 在新 event loop 中重新创建队列

### 4. 生产环境部署
在生产环境中，确保：
- Celery Worker 作为独立进程/容器运行
- 配置足够的 Worker 并发数（根据服务器资源）
- 监控 Celery 任务执行状态（使用 Flower 或 Prometheus）

export function AssessmentInitializationMonitor() {
  const [progress, setProgress] = useState(null);
  
  useEffect(() => {
    const interval = setInterval(async () => {
      const res = await fetch('/api/v1/learning/assessments/initialization-progress');
      const data = await res.json();
      setProgress(data);
      
      if (data.is_complete) {
        clearInterval(interval);
      }
    }, 5000); // 每5秒查询一次
    
    return () => clearInterval(interval);
  }, []);
  
  return (
    <div>
      <h3>Assessment Initialization Progress</h3>
      <progress value={progress?.completed} max={progress?.total_expected} />
      <p>{progress?.progress_percentage.toFixed(2)}% completed</p>
    </div>
  );
}
