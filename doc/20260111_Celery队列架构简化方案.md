# Celery 队列架构简化方案

**日期**: 2026-01-11  
**优先级**: P1 (架构优化)  
**影响范围**: Celery 配置、部署脚本

---

## 一、问题诊断

### 当前队列配置

```
队列名称      | 任务数量 | 任务列表
-------------|---------|----------------------------------
logs         | 1       | batch_write_logs
default      | 8       | generate_roadmap
             |         | resume_after_review
             |         | resume_from_checkpoint
             |         | generate_cover_image_task
             |         | batch_generate_cover_images_task
             |         | retry_single_content
             |         | cleanup_old_checkpoints
             |         | monitor_checkpoint_size
```

### 核心问题

#### 🔴 问题1：过度设计

**单一任务独占队列**：只有 `batch_write_logs` 使用 `logs` 队列，完全不符合成本效益。

```python
# backend/app/core/celery_app.py
task_routes={
    "app.tasks.log_tasks.batch_write_logs": {"queue": "logs"},
    # 其他 8 个任务使用 default 队列
},
```

#### 🔴 问题2：部署脚本不完整

**检查 `railway_entrypoint.sh`（第60-140行）**：
```bash
# 只配置了这些 worker
celery_content)    # content_generation 队列
celery_workflow)   # default 队列（处理路线图工作流）
celery_logs)       # ❌ 未发现此配置！
```

**结论：`logs` 队列可能根本没有 worker 在监听！**

#### 🔴 问题3：违反 MVP 原则

**不需要独立队列的理由：**

1. **日志任务已优化**：
   ```python
   @celery_app.task(
       ignore_result=True,  # ✅ 不存储结果
       max_retries=3,       # ✅ 轻量重试
   )
   ```

2. **任务量不大**：
   - 日志任务：批量写入（每批约 10-50 条）
   - 执行时间：< 100ms
   - 不属于高并发场景

3. **资源浪费**：
   - 需要单独启动 worker 监听 `logs` 队列
   - 增加部署复杂度
   - 配置和监控成本上升

4. **功能重复**：
   - Celery 支持任务优先级（`priority` 参数）
   - 可以通过优先级实现相同效果

---

## 二、整改方案（激进策略）

### 方案：删除 `logs` 队列，统一使用 `default` 队列

**核心思想：**
- ✅ 简化架构：单一队列，所有任务统一管理
- ✅ 降低复杂度：部署、监控、配置都更简单
- ✅ 符合 MVP 原则：当前规模不需要队列隔离
- ✅ 保留扩展性：未来如需隔离，再按业务需求划分

## 四、配置对比

### 修改前（复杂）

```yaml
队列配置:
  - logs (1 任务)
  - default (8 任务)

Worker 启动:
  worker1: --queues=logs --concurrency=2
  worker2: --queues=default --concurrency=6

部署复杂度: ⚠️ 高
  - 需要配置 2 个队列
  - 需要启动 2 个 worker
  - 需要监控 2 个队列状态
```

### 修改后（简化）

```yaml
队列配置:
  - default (9 任务)

Worker 启动:
  worker: --queues=default --concurrency=8

部署复杂度: ✅ 低
  - 单一队列
  - 单一 worker（或多个 worker 监听同一队列）
  - 简化监控
```

## 五、性能评估

### 日志任务特性分析

| 指标 | 值 | 说明 |
|-----|---|------|
| **任务执行时间** | < 100ms | 批量数据库插入 |
| **任务频率** | 中等 | 每个工作流节点 1-2 次 |
| **批次大小** | 10-50 条 | 已批量处理 |
| **失败影响** | 低 | 日志丢失不影响业务 |
| **优先级** | 低 | 可以延迟执行 |

**结论：不需要独立队列隔离。**

**观察：**
- 日志任务最轻量

- 不需要特殊隔离

## 七、扩展性考虑

### 何时需要重新划分队列？

**场景1：日志量激增**
- 触发条件：日志任务每秒 > 100 条
- 解决方案：
  ```python
  task_routes={
      "app.tasks.log_tasks.*": {"queue": "logs", "priority": 1},
  }
  ```

**场景2：需要独立的内容生成 worker 池**
- 触发条件：内容生成任务并发 > 20
- 解决方案：
  ```python
  task_routes={
      "app.tasks.content_utils.*": {"queue": "content_generation"},
  }
  ```

**场景3：需要不同的超时策略**
- 触发条件：某类任务需要特殊超时配置
- 解决方案：在任务装饰器中配置，无需独立队列

### 当前系统规模

```
日志任务量: 约 10-50 条/分钟 (低)
工作流任务: 约 5-10 个/小时 (低)
维护任务: 定时任务 (极低)
```

**结论：远未达到需要队列隔离的规模。**
