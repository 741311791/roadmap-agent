# 内容生成阶段双重错误修复

**修复日期**: 2026-02-08  
**严重程度**: 高（导致内容生成完全失败）  
**影响范围**: 
- 错误1: Quiz/Tutorial/Resource 元数据保存（时区冲突）
- 错误2: 内容生成子图执行（Event Loop跨循环）

---

## 📋 问题现象

### 错误日志
```
sqlalchemy.exc.DBAPIError: invalid input for query argument $9: 
datetime.datetime(2024, 6, 15, 12, 0, tz... 
(can't subtract offset-naive and offset-aware datetimes)

[SQL: INSERT INTO quiz_metadata (..., created_at, updated_at) ...]
```

### 触发条件
- Quiz/Tutorial/Resource 生成完成后保存元数据时
- PostgreSQL asyncpg 驱动检测到 datetime 类型不匹配
- 事务回滚导致后续操作全部失败

---

## 🧪 根因分析

### 物理层面：PostgreSQL 时区处理规则
- 数据库列定义：`TIMESTAMP WITHOUT TIME ZONE`
- asyncpg 驱动要求：datetime 对象的 `tzinfo` 必须与列定义匹配
- 不匹配后果：驱动在类型检查阶段抛出 `DataError`

### 逻辑层面：datetime 工厂函数错误
项目约定（`backend/app/models/database.py:3-8`）：
```python
# 所有时间字段统一使用北京时间 (UTC+8)
# 使用 TIMESTAMP WITHOUT TIME ZONE 存储，避免 PostgreSQL 自动转换为 UTC
# beijing_now() 返回无时区信息的北京时间
```

**违反约定的代码**（`backend/app/models/domain.py:792`）：
```python
class QuizGenerationOutput(BaseModel):
    created_at: datetime = Field(default_factory=datetime.now, ...)  # ❌ 错误
```

`datetime.now()` 返回带时区信息的 datetime（`tzinfo=TzInfo(0)`），与数据库定义冲突。

### 因果链条
```
Agent生成Output
  └─ created_at = datetime.now() (带时区)
    └─ CRUD保存元数据
      └─ asyncpg检查参数类型
        └─ offset-aware datetime vs TIMESTAMP WITHOUT TIME ZONE
          └─ 类型不匹配 → DataError ❌
            └─ 事务回滚 → session关闭
              └─ 后续查询 → InvalidRequestError ❌
```

#### 2.1 添加时区转换辅助函数
```python
def _ensure_naive_datetime(dt: datetime) -> datetime:
    """
    确保datetime对象无时区信息（防御性函数）
    
    如果输入的datetime带有时区信息，转换为北京时间并移除时区。
    如果已经无时区信息，直接返回。
    """
    if dt.tzinfo is None:
        return dt
    
    # 有时区信息，转换为北京时间（UTC+8）并移除时区
    from datetime import timezone, timedelta
    BEIJING_TZ = timezone(timedelta(hours=8))
    beijing_time = dt.astimezone(BEIJING_TZ)
    return beijing_time.replace(tzinfo=None)
```

#### 2.2 在保存前转换时区
```python
# ✅ 修复后
metadata = QuizMetadata(
    ...,
    created_at=_ensure_naive_datetime(quiz_output.created_at),
)
```

## 🔥 错误2详细分析

### 错误现象（修复时区后出现）
```
RuntimeError: <asyncio.locks.Lock object at 0x160123470 [locked]> 
is bound to a different event loop
```

### 根因分析

#### 公理：AsyncIO Event Loop线程局部性
- Event Loop创建的原语（Lock/Event）绑定到该loop
- 不同event loop不能共享asyncio原语
- 违反此公理会触发RuntimeError

#### 因果链条
```
Worker启动
  └─ setup_event_loop() 创建持久Loop A
    └─ OrchestratorFactory.initialize()
      └─ AsyncPostgresSaver创建Lock (绑定到Loop A)

Content Task执行  
  └─ asyncio.run() 创建临时Loop B ❌
    └─ 子图使用AsyncPostgresSaver
      └─ Lock.acquire() 在Loop B中失败
        └─ RuntimeError: bound to different loop
```

### 修复方案
**将所有Celery任务中的`asyncio.run()`替换为`run_async_in_worker_loop()`**

修改的文件：
1. `app/tasks/content_generation_tasks.py` (2处)
2. `app/tasks/maintenance_tasks.py` (2处)  
3. `app/tasks/cover_image_tasks.py` (1处)

修复前：
```python
result = asyncio.run(async_function())  # ❌ 创建新loop
```

修复后：
```python
from app.tasks.event_loop_manager import run_async_in_worker_loop

result = run_async_in_worker_loop(async_function())  # ✅ 使用持久loop
```

## 📝 经验总结

### 关键教训
1. **遵守项目约定至关重要**  
   database.py 开头已明确说明时间处理规范，但 domain.py 未遵守

2. **类型不匹配的隐蔽性**  
   `datetime.now()` 与 `beijing_now()` 在大多数情况下看起来相同，但时区属性导致数据库错误

3. **防御性编程的必要性**  
   即使修复了根因，CRUD 层仍需防御性检查

4. **AsyncIO在多进程环境的复杂性**  
   Celery Worker使用持久event loop，所有任务必须复用该loop，不能创建新的

5. **AsyncIO原语的生命周期绑定**  
   Lock/Event等原语在创建时绑定到当前event loop，跨loop使用会报错

### 最佳实践
1. 项目使用统一的时间工厂函数
2. 在 ORM 模型和 Pydantic 模型中保持一致
3. 数据库列定义与应用层处理匹配
4. 添加自动化测试验证时区处理正确性
5. **Celery任务中禁止使用`asyncio.run()`，必须使用`run_async_in_worker_loop()`**
6. **持久event loop架构下，所有asyncio操作必须在同一个loop中执行**
