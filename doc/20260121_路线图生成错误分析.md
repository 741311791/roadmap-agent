### 🔴 错误2: RoadmapMetadata缺少status字段

**错误信息**:
```
AttributeError: 'RoadmapMetadata' object has no attribute 'status'
```

**错误位置**: `backend/app/services/roadmaps/retrieval_service.py:93`

**错误代码**:
```python
"status": metadata.status or "draft",  # ❌ RoadmapMetadata 没有 status 字段
```

**发生时间**: 22:17:43, 22:19:29

**根本原因**:
- `RoadmapMetadata` 模型确实没有 `status` 字段
- 路线图状态应该从关联的 `Task` 对象中获取,而不是从 `RoadmapMetadata` 中获取

**数据模型关系**:
```
Task (有status字段)
  ├─ roadmap_id (外键)
  └─ status: "pending" | "processing" | "completed" | "failed"

RoadmapMetadata (无status字段)
  ├─ roadmap_id (主键)
  ├─ title
  ├─ learning_goal
  └─ ...
```

**修复方案**:
```python
# 错误代码 (backend/app/services/roadmaps/retrieval_service.py)
async def get_roadmap_with_status(db: AsyncSession, roadmap_id: str):
    metadata = await roadmap_crud.get_by_roadmap_id(db, roadmap_id)
    return {
        "status": metadata.status or "draft",  # ❌ 错误
        ...
    }

# 正确代码
async def get_roadmap_with_status(db: AsyncSession, roadmap_id: str):
    # 1. 获取元数据
    metadata = await roadmap_crud.get_by_roadmap_id(db, roadmap_id)
    if not metadata:
        raise NotFoundError(f"Roadmap {roadmap_id} not found")
    
    # 2. 获取关联的任务状态
    task = await task_crud.get_latest_by_roadmap_id(db, roadmap_id)
    task_status = task.status if task else "draft"
    
    return {
        "roadmap_id": metadata.roadmap_id,
        "user_id": metadata.user_id,
        "learning_goal": metadata.learning_goal,
        "framework": metadata.framework,
        "status": task_status,  # ✅ 从Task获取状态
        ...
    }
```

### 🟡 错误4: Intent Analysis 404

**错误信息**:
```
custom_api_exception: 未找到需求分析元数据
status_code: 404
```

**请求路径**: `GET /api/v1/roadmaps/095f8dba-c2cb-43c6-af65-93950789cf93/intent-analysis`

**发生时间**: 持续发生 (22:16-22:19)

**根本原因**:
- 前端在轮询获取需求分析结果
- 但在任务执行早期阶段,`IntentAnalysis` 数据尚未生成
- 或数据已生成但未正确保存到数据库

**业务流程**:
```
1. 用户提交生成请求
2. 创建Task (status=pending)
3. Celery任务启动
4. IntentAnalysis 执行中...  ← 此时前端请求会404
5. IntentAnalysis 完成并保存
6. 前端可以获取到数据
```

**修复方案**:

**方案1: 接口返回更友好的响应**
```python
# backend/app/api/v1/endpoints/roadmaps/metadata.py

@router.get("/{roadmap_id}/intent-analysis")
async def get_intent_analysis(
    roadmap_id: str,
    db: CurrentSession
) -> ResponseModel:
    """获取需求分析元数据"""
    
    # 1. 检查任务状态
    task = await task_crud.get_latest_by_roadmap_id(db, roadmap_id)
    if not task:
        raise NotFoundError("任务不存在")
    
    # 2. 如果任务还在执行中,返回任务状态
    if task.status in ["pending", "processing"]:
        return ResponseModel(
            success=True,
            message="需求分析正在进行中",
            data={
                "status": task.status,
                "current_step": task.current_step,
                "available": False  # ✅ 明确告知前端数据尚不可用
            }
        )
    
    # 3. 任务完成,获取数据
    intent_analysis = await intent_crud.get_by_roadmap_id(db, roadmap_id)
    if not intent_analysis:
        # 任务完成但数据缺失,说明有问题
        logger.error("intent_analysis_missing", roadmap_id=roadmap_id, task_id=task.task_id)
        raise NotFoundError("未找到需求分析元数据")
    
    return ResponseModel(
        success=True,
        data={
            "available": True,
            **intent_analysis.model_dump()
        }
    )
```

```python
# backend/app/agents/structure_validator.py

async def execute(self, input_data: ValidationInput) -> ValidationOutput:
    max_retries = 3
    for attempt in range(max_retries):
        try:
            response = await self.call_llm(prompt)
            return ValidationOutput.model_validate_json(response)
        except ValidationError as e:
            if "literal_error" in str(e) and attempt < max_retries - 1:
                # ✅ 将错误信息反馈给LLM,让其修正
                error_hint = f"上次输出错误: {e}. 请严格使用规定的action类型."
                prompt = self._rebuild_prompt_with_hint(input_data, error_hint)
                continue
            raise
```

### 🟢 错误6: Asyncio Event Loop冲突

**错误信息**:
```
RuntimeError: <Queue at 0x10846aa20 maxsize=50000 tasks=1> is bound to a different event loop
```

**错误位置**: `litellm/litellm_core_utils/logging_worker.py`

**发生时间**: 22:17:42, 22:18:12

**根本原因**:
- Celery Worker和FastAPI使用不同的event loop
- LiteLLM的日志Queue绑定到旧的event loop
- 当Celery Worker重启或Event Loop切换时,Queue失效

**影响**:
- 仅影响LiteLLM的日志记录功能
- 不影响实际的LLM调用和业务逻辑

**修复方案**:
```python
# backend/app/core/celery_app.py

from celery.signals import worker_process_init
import asyncio

@worker_process_init.connect
def init_worker_process(**kwargs):
    """Celery Worker进程初始化时重置event loop"""
    # 确保每个Worker进程有独立的event loop
    loop = asyncio.new_event_loop()
    asyncio.set_event_loop(loop)
    
    # 重新初始化LiteLLM (如果需要)
    # litellm.reset_logging_queue()
```

或者在配置中禁用LiteLLM的异步日志:
```python
# backend/app/config/settings.py

import litellm

# 禁用异步日志,使用同步日志
litellm.set_verbose = False
litellm.callbacks = []  # 移除回调
```

## 四、系统性改进建议

- **问题**: `RoadmapMetadata` 和 `Task` 的关系混乱
