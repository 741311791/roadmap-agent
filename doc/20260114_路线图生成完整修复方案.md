## 问题1：数据库连接池跨进程污染

### 错误现象
```
ForeignKeyViolationError: insert or update on table "tutorial_metadata" violates foreign key constraint "tutorial_metadata_roadmap_id_fkey"
DETAIL: Key (roadmap_id)=(python-fullstack-engineer-b4k9m2n7) is not present in table "roadmap_metadata"
```

### 根因
在 Celery Worker 子进程中混用了 FastAPI 的连接池（`async_session_maker`），导致跨进程连接状态污染，事务可见性被破坏。

### 修复方案
统一使用 Celery 专用 Session（`get_celery_session()`），使用 NullPool 避免连接池状态共享。

### 修复文件
- `backend/app/core/orchestrator/subgraphs/single_concept_content_generation.py`
- `backend/app/core/orchestrator/subgraphs/content_generation.py`
- `backend/app/tasks/content_generation_tasks.py`

### 详细文档
参见：`20260114_数据库连接池跨进程污染修复.md`

## 问题2：节点数据传递不完整

### 错误现象
- 日志显示 `curriculum_design` 节点"执行成功"
- 数据库中没有对应的 `roadmap_metadata` 记录

### 修复方案
在所有节点的返回值中补全 Handler 需要的字段。

## 问题3：ContentHandler初始化错误

### 错误现象
```
NodeOutputHandler.__init__() got an unexpected keyword argument 'notification_service'
```

### 根因
`ContentHandler` 在子图中被创建时，传递了多余的参数：
- `notification_service`
- `execution_logger`
- `state_manager`

但 `NodeOutputHandler` 基类只接受 `state_manager` 一个参数。

### 修复方案
```python
# ❌ 修复前
handler = ContentHandler(
    notification_service=ctx.notification_service,
    execution_logger=ctx.execution_logger,
    state_manager=ctx.state_manager,
)

# ✅ 修复后
handler = ContentHandler(
    state_manager=ctx.state_manager,
)
```

- `backend/app/core/orchestrator/subgraphs/content_generation.py`

## 问题4：ConceptMetadata查询失败

### 错误现象
```
ValueError: ConceptMetadata not found for concept_id: python-fullstack-engineer-b4k9m2n1:c-4-2-2
```

但查询数据库后发现该 `concept_id` 的数据是存在的。

### 根因
在 `concept_content_handler.py` 中：
1. 先创建了 `ConceptMetadata` 记录（第199行）
2. 但没有立即 `flush()` 到数据库
3. 后续调用 `update_content_status()` 时（第207行），该方法内部查询 `ConceptMetadata`（第417行）
4. 由于没有 flush，同一事务内的查询返回 None，抛出 ValueError

**事务可见性问题**：
- 在同一事务内，未 flush 的数据对后续查询不可见
- 用户查询时，事务已经 commit，所以能看到数据

### 修复方案
```python
# ✅ 修复后
concept_metadata = await concept_crud.create_or_update_metadata(
    session=session,
    concept_id=concept_id,
    roadmap_id=roadmap_id,
)
# ⚠️ 立即 flush 确保后续查询能看到这条记录
await session.flush()
```

- `backend/app/core/orchestrator/handlers/concept_content_handler.py`

## 问题6：Tavily API速率限制

### 错误现象
```
tavily_api_search_failed error='Your request has been blocked due to excessive requests. 
Please reduce the rate of requests. Verify you are using production API keys.' 
error_type=UsageLimitExceededError
```

### 根因分析

**当前实现**：
- 使用全局 `GlobalRateLimiter`（基于 Redis）
- 限制：100 次/分钟（所有 API key 共享）
- Key: `rate_limiter:tavily_api`

**问题所在**：
- Tavily API 的速率限制是**针对每个 API key** 的
- 我们的全局限制器是**所有 key 共享**的
- 即使全局没有超过 100 次/分钟，单个 key 可能已经超过了自己的限制

**示例场景**：
```
假设有3个 Tavily keys：key1, key2, key3
每个 key 的限制是 100 次/分钟

当前实现：所有 key 共享全局限制 100 次/分钟
- key1 被使用了 80 次 ❌ 可能已超过单 key 限制
- key2 被使用了 15 次 ✅
- key3 被使用了 5 次 ✅
- 全局：100 次（未超限）✅
- 结果：key1 触发 API 限流
```

### 临时缓解方案

#### 方案1：降低全局限制

```python
# backend/app/utils/rate_limiter.py
_tavily_rate_limiter = GlobalRateLimiter(
    redis_client=redis_client,
    key_prefix="tavily_api",
    max_requests=50,  # ✅ 从 100 降低到 50
    window_seconds=60,
)
```

**效果**：
- 减少单个 key 的使用频率
- 但仍无法解决根本问题（多 key 不均衡）

#### 方案2：增加 API Keys

在 `tavily_api_keys` 表中添加更多 keys，分散请求压力。

---

### 长期解决方案（需要重构）

#### 架构改进：为每个 Key 创建独立限制器

```python
# backend/app/utils/rate_limiter.py

_tavily_key_limiters: dict[str, GlobalRateLimiter] = {}

async def get_tavily_rate_limiter_for_key(api_key: str) -> GlobalRateLimiter:
    """
    获取特定 Tavily API key 的速率限制器
    
    每个 key 独立限制：100 次/分钟
    
    Args:
        api_key: Tavily API key
        
    Returns:
        该 key 的专属限制器
    """
    import hashlib
    
    # 使用 key 的 hash 作为标识（避免泄露完整 key）
    key_hash = hashlib.sha256(api_key.encode()).hexdigest()[:16]
    
    if key_hash not in _tavily_key_limiters:
        from redis.asyncio import from_url
        
        redis_client = from_url(
            settings.get_redis_url,
            encoding="utf-8",
            decode_responses=False,
        )
        
        # 为该 key 创建独立限制器
        _tavily_key_limiters[key_hash] = GlobalRateLimiter(
            redis_client=redis_client,
            key_prefix=f"tavily_api:{key_hash}",  # ✅ 每个 key 独立
            max_requests=100,
            window_seconds=60,
        )
        
        logger.info(
            "tavily_key_limiter_created",
            key_hash=key_hash,
            max_requests=100,
        )
    
    return _tavily_key_limiters[key_hash]
```

#### 修改 TavilyAPISearchTool

```python
# backend/app/tools/search/tavily_api_search.py

async def _rate_limited_request(self, func, api_key: str, *args, **kwargs):
    """
    带速率限制的请求包装器（优化版）
    
    改进：
    - 为每个 API key 使用独立的速率限制器
    - 避免全局限制导致的单点超限
    """
    from app.utils.rate_limiter import get_tavily_rate_limiter_for_key
    
    # ✅ 获取该 key 的专属限制器
    rate_limiter = await get_tavily_rate_limiter_for_key(api_key)
    
    async with self._search_semaphore:
        try:
            await rate_limiter.acquire(timeout=30.0)
        except TimeoutError as e:
            logger.error(
                "tavily_api_rate_limit_timeout",
                key_hash=api_key[-8:],  # 只显示最后8位
                message=str(e),
            )
            raise ValueError("Tavily API rate limit exceeded, please try again later")
        
        result = await asyncio.to_thread(func, *args, **kwargs)
        
        current_count = await rate_limiter.get_current_count()
        logger.debug(
            "tavily_api_request_executed",
            key_hash=api_key[-8:],
            requests_in_last_minute=current_count,
            max_requests=100,
        )
        
        return result
```

## 架构改进总结

### 1. Session 管理一致性

**规则**：
- ✅ FastAPI API 端点 → `CurrentSession` / `CurrentSessionTransaction`
- ✅ Celery Task 和 LangGraph Node → `get_celery_session()`
- ✅ 子图内部 → `get_celery_session()`

**原理**：
- FastAPI 使用连接池（高并发）
- Celery 使用 NullPool（进程隔离）

---

### 2. 节点输出完整性

**规则**：
- ✅ 节点返回值必须包含 Handler 所需的所有字段
- ✅ 添加注释标记 `⚠️ 必须包含 Handler 需要的所有字段`
- ✅ 字段来源：Agent 输出 > State > 输入参数

**模板**：
```python
async def my_node(state: RoadmapState, config: RunnableConfig) -> dict:
    # ... 执行逻辑 ...
    
    # 返回纯数据（不保存数据库）
    # ⚠️ 必须包含 Handler 需要的所有字段
    return {
        "core_output": agent_result,              # Agent 核心输出
        "roadmap_id": state["roadmap_id"],        # ✅ Handler 需要
        "user_id": state["user_request"].user_id, # ✅ Handler 需要
        "current_step": "my_node",
        "execution_history": ["节点完成"],
    }
```

---

### 3. 事务可见性保证

**规则**：
- ✅ 关键数据创建后立即 `flush()`
- ✅ 确保同一事务内的后续查询可见
- ✅ 避免 "not found" 错误

**示例**：
```python
# 创建记录
new_record = await crud.create(session, obj)

# ⚠️ 立即 flush（如果后续需要查询）
await session.flush()

# 后续查询可见
record = await crud.get_by_id(session, new_record.id)
assert record is not None  # ✅ 通过
```

---

### 4. 日志输出规范

**规则**：
- ✅ 生产环境：只记录 WARNING 及以上
- ✅ 开发环境：记录 INFO 及以上
- ✅ 调试模式：记录 DEBUG（含简化堆栈）
- ✅ Agent 输出：自动截断到 50 字符
