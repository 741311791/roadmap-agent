# 聊天前端移植进展与后续计划

## 一、当前阶段目标

本阶段目标不是继续在现有 `mentor` 侧边栏 UI 上做增强，而是逐步把 `deer-flow` 的聊天前端体验移植到当前项目中，并通过主 `FastAPI` 代理 deer-flow 后端能力，验证这条方案是否能形成独立可用的产品链路。

当前采用的总体架构为：

- 前端只请求主应用 `FastAPI`
- 主应用负责鉴权、路线图权限校验、业务上下文注入
- 主应用再把聊天请求转发给独立部署的 `deer-flow` gateway
- `deer-flow` 负责 thread / run / SSE / memory queue 等运行时能力

## 三、当前结论

到目前为止，可以确认以下几点：

### 1. 技术方案可行

“主 `FastAPI` 代理 + 独立 deer-flow 后端 + 独立移植聊天前端” 这条方案已经被真实联调验证可行。

### 2. 后端链路稳定

主应用代理 deer-flow 的 thread / chat / message 链路已经可以实际工作，后续重点不再是“能不能通”，而是“如何更完整地承载 deer-flow 原生前端体验”。

### 3. 体验问题主要在前端移植深度不够

当前独立测试页已经比最初的轻量实现更接近 deer-flow 原版，但仍不是完整的 `workspace/chats/[thread_id]` 原生镜像。

差距主要在：

- 原版 `InputBox` / `PromptInput` 已接入第一版，但 model selector / suggestions / 上传态等能力仍未完整迁完
- 原版 `MessageListItem` / `MessageList` 已接入第一版，但文件卡片、toolbar、subtask 卡片等细节仍未补齐
- 原版 `ChatBox` 与 artifact 分栏已接入 provider 骨架，但 artifact detail/list 仍是占位态
- 原版 `core/threads`、`core/messages`、`core/tasks` 仍只移植了最小可用桥接层

## 五、当前建议

建议继续沿当前方向推进，而不要再回到旧 `mentor` 侧边栏上做适配。

原因：

- 旧 `mentor` 链路的模型体系、消息结构、状态管理方式与 deer-flow 原版不同
- 越往后修补，越难获得 1:1 原生体验
- 当前独立测试页已经证明独立移植路线是可行的

最合理的下一步是：

- 继续扩大 deer-flow 原生前端组件和数据链路的移植范围
- 把当前测试页逐步演进成真正的 deer-flow 原生聊天页

## 六、已知风险

- deer-flow 原版前端依赖链较深，继续移植会涉及较多组件与 `core/*` 目录
- 你当前前端使用的是自己的设计系统和项目结构，完全 1:1 复制会带来一定整合成本
- 主后端代理接口与 deer-flow LangGraph SDK 的原生接口形状仍有差异，后续若移植到更深层 hook，可能还需要继续做接口桥接
