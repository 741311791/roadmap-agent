## 一、架构指南的 Session 管理标准

### 指南推荐实现（Line 264-299）

```python
# ✅ 读操作 Session (无自动commit)
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    """只读操作使用"""
    async with async_db_session() as session:
        yield session
        # 自动关闭，但不commit

# ✅ 写操作 Session (自动commit/rollback)
async def get_db_transaction() -> AsyncGenerator[AsyncSession, None]:
    """写操作使用"""
    async with async_db_session.begin() as session:
        yield session
        # 成功自动commit，异常自动rollback

# Annotated 简化注入
CurrentSession = Annotated[AsyncSession, Depends(get_db)]
CurrentSessionTransaction = Annotated[AsyncSession, Depends(get_db_transaction)]
```

**特点**：
- ✅ **极简设计**：直接使用 SQLAlchemy 的会话管理
- ✅ **责任明确**：依赖 SQLAlchemy 的健壮性
- ✅ **易于理解**：新人 5 分钟即可掌握
- ✅ **零防御性编程**：信任底层库的异常处理

### 2.2 过度防御性编程清单

#### ❌ 问题 1: 多层异常捕获

```python
# 当前实现（Line 771-852）

    session = None
    request_cancelled = False
    
    try:
        session = AsyncSessionLocal()
        yield session
    except asyncio.CancelledError:
        request_cancelled = True
        logger.warning("请求被取消，强制清理数据库会话")
        raise
    except GeneratorExit:
        logger.debug("db_session_generator_exit")
    finally:
        if session is not None:
            try:
                await asyncio.sleep(0)  # ❌ 不必要的等待
                await asyncio.shield(session.close())  # ❌ 过度保护
                # ... 更多异常处理 ...
            except IllegalStateChangeError:
                # ... 静默处理 ...
            except asyncio.CancelledError:
                # ... 更多处理 ...
            except Exception as e:
                # ... 更多处理 ...
```

**问题**：
- ❌ 使用 `asyncio.shield()` 防止取消（SQLAlchemy 自己会处理）
- ❌ 捕获 `GeneratorExit`（应该让它自然传播）
- ❌ 捕获 `IllegalStateChangeError`（应该暴露问题）
- ❌ 多层 try-except 嵌套（降低可读性）

#### ❌ 问题 2: 重试机制过度复杂

## 三、根本原因分析

### 3.1 为什么会过度工程化？

#### 原因 1: 症状治疗 vs 根本治疗

```
问题症状：生产环境出现连接泄漏
  ↓
❌ 错误应对：在 session.py 中增加防御性代码
  - 添加 asyncio.shield()
  - 添加多层异常捕获
  - 添加连接池监控
  ↓
✅ 正确应对：找到连接泄漏的根本原因
  - 哪个 API 端点没有正确关闭会话？
  - 哪个 Celery 任务有异常路径未处理？
  - 是否有代码直接创建会话但未关闭？
```

#### 原因 2: 缺乏对 SQLAlchemy 的信任

**SQLAlchemy 2.0 已经非常健壮**：
- ✅ `async with session` 会自动关闭会话
- ✅ `async with session.begin()` 会自动 commit/rollback
- ✅ 连接池会自动管理连接生命周期
- ✅ 异常会正确传播到调用方

**我们的防御性编程暗示**：
- ❌ 不信任 SQLAlchemy 的会话管理
- ❌ 不信任 Python 的上下文管理器
- ❌ 不信任 asyncio 的取消机制

#### 原因 3: 职责边界模糊

| 职责 | 应该由谁负责 | 当前谁在负责 |
|------|------------|------------|
| 连接池管理 | SQLAlchemy Engine | ✅ SQLAlchemy |
| 会话生命周期 | SQLAlchemy Session | ⚠️ safe_session() |
| 事务管理 | SQLAlchemy Transaction | ⚠️ get_db_transaction() |
| 连接泄漏检测 | Prometheus 指标 | ✅ Prometheus |
| 连接泄漏修复 | **业务代码（调用方）** | ❌ **session.py** |

## 四、重构建议

### 4.1 极简重构方案（推荐）⭐

```python
# backend/app/db/session.py (重构后，约 100 行)

from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine, async_sessionmaker
from typing import AsyncGenerator
from fastapi import Depends

# ============================================================
# 引擎和会话工厂
# ============================================================

engine = create_async_engine(
    settings.DATABASE_URL,
    echo=False,
    pool_size=settings.DB_POOL_SIZE,
    max_overflow=settings.DB_MAX_OVERFLOW,
    pool_pre_ping=True,
    pool_recycle=300,
    pool_timeout=60,
)

async_session_maker = async_sessionmaker(
    engine,
    class_=AsyncSession,
    expire_on_commit=False,
    autocommit=False,
    autoflush=False,
)

# ============================================================
# Session 依赖注入（读写分离）
# ============================================================

async def get_db_readonly() -> AsyncGenerator[AsyncSession, None]:
    """
    只读 Session（GET 请求使用）
    
    特性：
    - 不自动 commit
    - 异常自动关闭会话
    """
    async with async_session_maker() as session:
        yield session
        # ✅ SQLAlchemy 自动处理关闭


async def get_db_transaction() -> AsyncGenerator[AsyncSession, None]:
    """
    事务 Session（POST/PUT/DELETE 使用）
    
    特性：
    - 成功自动 commit
    - 异常自动 rollback
    """
    async with async_session_maker.begin() as session:
        yield session
        # ✅ SQLAlchemy 自动处理 commit/rollback


# ============================================================
# 类型别名
# ============================================================

CurrentSession = Annotated[AsyncSession, Depends(get_db_readonly)]
CurrentSessionTransaction = Annotated[AsyncSession, Depends(get_db_transaction)]


# ============================================================
# Prometheus 监控（可选）
# ============================================================

async def get_pool_status() -> dict:
    """连接池状态监控"""
    pool = engine.pool
    return {
        "pool_size": pool.size(),
        "checked_out": pool.checkedout(),
        "overflow": pool.overflow(),
        "checked_in": pool.checkedin(),
    }
```

**重构效果**：
- ✅ 从 1029 行 → 约 100 行（90% 减少）
- ✅ 零防御性编程
- ✅ 完全符合架构指南
- ✅ 易于理解和维护

### 4.2 Celery 专用会话（保留独立文件）

```python
# backend/app/db/celery_session.py (简化后，约 50 行)

from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from sqlalchemy.pool import NullPool

# Celery Worker 使用 NullPool（避免 Fork 问题）
celery_engine = create_async_engine(
    settings.DATABASE_URL,
    echo=False,
    poolclass=NullPool,  # ⭐ 关键：每次都创建新连接
    pool_pre_ping=True,
)

celery_session_maker = async_sessionmaker(
    celery_engine,
    expire_on_commit=False,
)


async def get_celery_session() -> AsyncGenerator[AsyncSession, None]:
    """Celery 任务专用会话"""
    async with celery_session_maker.begin() as session:
        yield session
        # ✅ 自动 commit/rollback
```

**保留理由**：
- ✅ Celery Worker 有 Fork 进程隔离需求
- ✅ NullPool 是 Celery 的最佳实践
- ✅ 简化后仍然易于维护

## 八、核心原则总结

### ✅ 应该遵循的原则

1. **KISS 原则**（Keep It Simple, Stupid）
   - 简单的代码 = 更少的 Bug
   - 优先使用库的默认行为

2. **YAGNI 原则**（You Aren't Gonna Need It）
   - 不要为"可能的问题"编写代码
   - 等问题真实出现再解决

3. **信任成熟的库**
   - SQLAlchemy 2.0 已经过数百万项目验证
   - 不要重新发明轮子

4. **职责边界清晰**
   - session.py 只负责提供会话
   - 连接泄漏由调用方负责

### ❌ 应该避免的反模式

1. **过度防御性编程**
   - 不是所有异常都需要捕获
   - 让异常在正确的层级处理

2. **症状治疗**
   - 不要在底层库中修复业务代码的问题
   - 找到根本原因

3. **缺乏信任**
   - 不要因为一次生产问题就失去对库的信任
   - 分析问题真正的原因
